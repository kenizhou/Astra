# 发送：Astra Mail 契约

**范围。** 从按下发送那一刻起发生的一切：持久发件队列、一封邮件绝不发送两次的
规则、未确认送达的含义、排队中的发送所能执行的操作，以及发件人自己的副本。
对每一个搭载编写器或发件箱的界面都有约束。实质上移植自 mail-calendar 的
`sending.md`，并按 Astra Mail 今日实际交付的范围裁剪；缺口记录在文末，
绝不静默略过。

**原则。** *投递一封邮件与保留发件人的副本是两件不同的事，客户端绝不能让后者
无声地失败。* Sent 副本是一个人核对邮件确实已发出的依据；无声地丢失它，比
大多数会打断用户的失败更糟，因为事后没有任何东西能把它找回来。

## 绝不发送两次

邮件客户端里唯一不可逆的行为，是把一封邮件第二次送到收件人面前。以下每一条
规则都服从于它。

- **在请求任何服务器之前，发送先进队列。** `Intent::SubmitRichMail` 通过编写器
  crate 的确定性渲染器渲染编写器文档，铸造全新的 `Message-ID`，并把邮件交给
  引擎的 `submit_mail`；后者在触碰提供方之前先记录该操作（以该 `Message-ID`
  幂等）。此后无论进程在哪个时刻结束，这封邮件既不会丢失，也不会投递两次。
- **引擎在不可折返点记录交接**：可能完成投递的最后一个字节。它之前的一切
  （连接、登录、传输头部）都可以安全重复；在那之前被切断的发送会重试，在
  那之后被切断的发送可能已经到达收件人手中，转而等待用户的答复。
- **可能已投递的发送绝不擅自重发。** 重新连接、立即发送和取消在它上面一律被
  拒绝。它的副本出现在 Sent 文件夹里即可解决；否则由用户以**标记为已发送**或
  **再次发送**作答。
- **存储会拒绝发给一个并不在等待答复的发送的答复**，因此状态在点击之下已
  变化的行无法发送两次：确认这一对答复只被发出询问的那一行、恰好一次地
  回答。
- **无法构造邮件的提交既不发送也不排队**：没有可用的发件账户、没有可解析的
  收件人、文档渲染失败，或主机未解析出字节的附件。静默缺失附件的邮件，比
  不发送更糟。纯邮件账户是诚实的例外：提交检查只询问账户是否有提供方，因此
  它的发送会入队，第一次排空将其落定为 Failed，连同载荷一起立在发件箱里。

## 持久队列

**应用接受的邮件属于用户，它不会因为服务器没有应答而蒸发。** 值得重试的失败
所对应的发送留在发件队列里，一个由引擎持有的持久队列，等到能够发出时自己
发出。

- **排队不是失败。** 告诉用户一个排队中的发送已失败，会诱使他们把邮件再写
  一遍，然后第一封也到了。排队中的发送读作四种状态之一：`Queued`、
  `Sending`、`Unconfirmed`、`Failed`，只有 `Failed` 意味着不会再有重试。
- **哪些失败进队列由引擎决定，而不是由界面决定**：可重试的一类停靠操作，
  其余的落定。应用询问队列邮件是否仍在，而不是重读错误，因此规则只有一条，
  且在拥有它的那一处。
- **排队中的发送在入队的那一刻就显示在屏幕上，离线也不例外。** 队列住在存储
  里而不是服务器上，所以离线不是不显示它的理由，而离线本来就是发送进队列的
  常见原因。所有账户的发送经由同一个 `Surface::Sending` 快照发布，队列的每次
  迁移（一封发送加入、离开或改变状态）都发布一次。
- **队列靠手势排空，而不是靠定时器**：每次同步过程结束时、每次提交时，以及
  用户按下立即发送时。定时器会在电池供电下唤醒死去的网络。第四个信号，设备
  重新上线，随重连工作一起到来，作为缺口记录在下文。
- **只有发送出现在队列里。** 排队中的草稿保存或关键字修改是对已经住在某个
  文件夹里的邮件的写入，文件夹才是其主人寻找它的地方。它们在后台排空，绝不
  显示为未发送的邮件。
- **被拒绝的发送被保留。** 重试无法挽救的拒绝把发送落定为未发送，队列保留
  它，连同载荷，直到用户再次发送或将其撤回。重新连接绝不会再次发送它：它
  加急的是等待中的邮件，不是被拒绝的邮件。
- **每一步都留下一行日志**（只有计数和 id：邮件属于用户，任何内容、收件人
  或主题都不写入日志）。

### 排队中的发送提供什么

| 状态 | 面板显示 | 提供的操作 |
|---|---|---|
| Queued | Queued | Send now · Cancel |
| Sending | Sending | 无：它无法被召回 |
| Unconfirmed | Unconfirmed | Mark as sent · Send again |
| Failed | Failed | Send again · Cancel |

| 操作 | Intent | 做什么 | 何时被拒绝 |
|---|---|---|---|
| **Send now**，被拒发送上的 **Send again** | `SendNow` | 清除退避，或把被拒的发送放回队列，并在同一手势内排空 | 正在发送中，或等待确认 |
| **Cancel** | `Cancel` | 撤回它，使其绝不会被投递 | 同上 |
| **Mark as sent** | `ConfirmSent` | 将其落定为已送达；它离开队列 | 发给不在等待答复的发送 |
| **未确认发送上的 Send again** | `ConfirmNotSent` | 把它放回队列并立即排空：可能已发送的邮件被再次尝试的唯一途径 | 同上 |

**未确认的行只提供用户的答复。** 邮件可能已经在收件人面前，所以任何界面都
不在它上面提供立即发送或取消，它的 Send again 发送的是 `ConfirmNotSent`，
绝不是 `SendNow`。两个 Send again 按钮读起来一样，因为对用户而言它们是同一个
请求；区分它们的是 intent，正是它让未确认的那一封无法经任何其他途径发出。
未确认是一种警示，绝不是失败，也绝不是等待：“发送失败”会招来第二份副本，
“等待发送”则许诺一个不会自己发生的尝试。

**一旦按下发送，发件队列就是这封邮件的唯一去处。** 提交携带的是编写器当前
的文档，不是它已存储的草稿，成功的发送会一并带走该编写的自动保存草稿，
因此一封邮件永远不会有两份副本都面临被发送。从未到达队列的发送会把
草稿留下，因为没有别的地方保有这些文字。

## 发件人的副本

在 IMAP/SMTP 上，投递与归档确实是两个往返：SMTP 每次发送重新拨号，副本由
单独的 `APPEND` 归档进账户的 Sent 文件夹。引擎在投递之后归档副本，并会在新的
连接上重试归档，先在 Sent 中搜索邮件自己的 `Message-ID` 使之幂等。

- **未归档的副本绝不让发送失败。** 邮件已经到达收件人手中，绝不能重发；结果
  说的是副本缺失，应用将其记为警告而不是吞掉。
- **结果绝不表述为发送失败。** 投递并归档的发送安静地结束；发送结果提示监视
  队列，在一封发送不是经由用户自己的手移除而离开队列时说 "Message sent"。
  用户自己做出的移除（取消、标记为已发送）不读作送达，而被拒绝的移除会把
  记号交还：主机的拒绝立刻交还，引擎的拒绝（发送在点击之下已进入发送中）
  在随后的快照上交还，因此该发送随后真正的送达仍然会被提示。
- **常驻的未归档副本问题的重试尚未交付**，作为缺口记录在下文。

## 规则

1. **绝不把未确认或未归档的发送表述为失败。** 这里唯一造成真实伤害的行为是
   把一封邮件发送两次，每一个措辞都以是否在招致它来衡量。
2. **引擎持有每个队列决策的两端**：什么到期、失败是停靠还是落定、一个操作
   能否被撤回或作答。界面只映射快照持有的内容，绝不重新推导队列规则；拒绝
   是日志里的文字，不是无声的空操作。
3. **操作指名它所在的行，而不是它的位置**：每个发件箱操作都携带排队发送的
   账户与操作 id，因此在点击之下移动过的行不会作用到它旧的邻行上。
4. **提交进行中以及未设置收件人时，发送被禁用**，因此一个手势无法排队两次
   发送，入队前的拒绝也不会发布任何界面需要撤销的东西。
5. **发送的失败界面保留文字。** 类型化错误让编写器保持打开、文档完好；队列
   是已尝试内容的记录，绝不是找回文字的地方。

## 已知缺口

- **Edit 尚未交付。** 把排队中的发送移回 Drafts 需要附件切片的暂存目录流程，
  因此被拒的发送只能再次发送或撤回，不能编辑。intent 家族作为延后项记录。
- **未确认发送上的 Send again 不先询问。** mail-calendar 的契约会在这个唯一
  失误会落到他人收件箱的操作前放一个确认问题；Astra Mail 的面板直接发送
  `ConfirmNotSent`。该问题随对话框批次落地。
- **未归档副本问题没有界面。** 投递成功但 Sent 副本未能归档的发送只留下日志，
  提示无法把它与干净的发送区分开，因此常驻问题及其修复要等对应界面交付。
- **没有由可达性驱动的排空。** 队列在同步过程、提交和立即发送时排空；设备
  重新上线既不排空队列也不清除各操作的超避，因为尚未接线重连信号。
- **应用关闭打断的发送由引擎契约与单元替身证明，而非由在线 harness 证明。**
  在测试中杀死一个发送中途的进程是 harness 尚不具备的能力；恢复路径
  （启动时的 `recover_outbox`）在每次真实启动时都会运行。
- **发件人的名字就是账户地址。** 尚未询问或存储按账户的对外名称，因此邮件以
  账户拨号所用的裸地址发出；From 选择器及其默认值随其切片到来。
- **回复与转发不做预填。** 本契约只覆盖在编写器中新写的邮件；引用与发件人
  预填随回复切片到来。
