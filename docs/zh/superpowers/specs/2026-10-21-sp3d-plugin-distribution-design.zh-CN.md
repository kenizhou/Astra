# SP3d 设计：插件分发

**状态。** 2026-10-21 已定稿。从 main 切出 `sp3d-plugin-distribution`
（SP3a/b/c 已合并）。来源：已批准插件计划的 Track A 阶段 4，加上前两个
切片记录的两笔欠账：授权持久化与非开发版对 proposed 方法插件的拒绝。

**范围。** 签名包及其验证、安装与同意流程、跨重启持久的授权与启用状
态、管理策略开关，以及非开发版对 proposed 方法的拒绝。不在本切片：策
划商店（计划中的"以后"）、密钥轮换与吊销基础设施、自动更新。

## D1：包是 tar 格式，ed25519 签名，自我标识

`.astra-plugin` 是插件目录的未压缩 tar：`manifest.toml`、worker 二进
制、frame 资源，外加 `publisher.pub`（发布者的 ed25519 公钥，同时以 hex
形式出现在 manifest 新增的 `publisher` 字段）与 `signature.bin`。签名覆
盖规范摘要：除 `signature.bin` 外每个条目的 (路径, sha256(内容)) 对排序
后的 sha256。验证即防篡改加身份：签名必须对 manifest 所指的发布者密钥验
证通过，途中的任何改写都得到拒绝；发布者指纹显示在同意对话框中。这有
意不是证书链：信任决定在安装时由人做出，与各处侧载的形态相同，记录在
案。

## D2：生产版验证，开发模式侧载

在开发模式之外（`ASTRA_PLUGIN_DEV` 未设置且为发布构建），安装拒绝未签
名或无法验证的包。开发模式维持今天的流程：受管插件目录下的目录树或
`ASTRA_PLUGIN_DEV` 路径免签名加载。`cargo run -p xtask -- bundle-plugin
<dir> <key>` 构建并签名一个包，工具链就在仓库自身。

## D3：安装是先报价后同意

设置页的 Plugins 页新增"从文件安装"：宿主验证并解析包，回答一份报价
（id、名称、版本、发布者指纹、所请权限、隐私政策 URL）。同意对话框逐项
列出所请权限（复选框默认不勾，失败关闭）、发布者与政策链接，以及安装
或取消。安装把包解进受管插件目录，记录所勾授权，并保持插件停用，直到
用户启用它。`plugin_install_offer` 与 `plugin_install` 是两条命令；报价
计算的内容安装时全部重新验证。

## D4：授权与启用状态持久

注册表在每次 approve 与 install 时向受管插件目录旁写入
`grants.toml`：每插件的已授予集合与是否启用。启动时读取：授权在任何
worker 启动前落地，记录为启用的插件在启动时启用（失败则进入 Failed，
绝不使启动失败）。注册表的内存表是写穿缓存；文件才是跨重启的真相。

## D5：管理策略开关

一个持久化的 `plugins_enabled` 偏好（默认开）随设置快照新增的 plugins
块下发。关意味着：启动不启用任何插件、`enable` 被拒绝、闸门/解码器/调
用端面视同没有任何插件在服务（注册表的 serving/call 路径查询该开
关）。Plugins 设置页持有该开关；注册表与各端面实时跟随。

## D6：生产版拒绝 proposed 方法插件

路由器已在非开发版拒绝 proposed 调用。分发补上加载时的拒绝：生产构建
不启用 manifest 声明了任何 proposed 方法的插件，使发布版绝不运行占位
API。开发版照常路由它们。

## D7：证明

单元红灯钉住：包的往返（构建、签名、验证、解出）、防篡改拒绝（翻转一
字节、错误密钥、生产模式下缺签名）、授权文件（写入、重读、启用标
记）、proposed 拒绝（开发版 vs 生产版）、策略开关（关则拒绝 enable 且
服务集合为空）、同意流程（报价点名一切，安装只持久化所勾集合）。web 钉
住同意对话框（权限默认不勾，Install 恰好携带所勾集合）与 Plugins 页的
开关。harness 冒烟维持 SP3b 闸门套件，在注册表读取持久化文件后必须保持
绿。

## 已记录的已知缺口，不隐藏

- 发布者密钥是自我声明的（侧载信任）；带发布者身份验证的策划商店是计
  划中的"以后"。
- 没有密钥轮换或吊销：发布者密钥泄露意味着在商店存在之前换新插件
  id。
- 同意对话框中每项权限的措辞是线名的友好渲染；更丰富的逐权限文案随商
  店落地。
- 不做自动更新；新包以替换方式覆盖旧目录安装。
