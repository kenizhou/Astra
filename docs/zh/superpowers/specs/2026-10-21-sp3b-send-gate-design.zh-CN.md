# SP3b 设计：发送闸门与编写器变换

**状态。** 2026-10-21 已定稿。在 PR #31 合并前，本切片从
`sp3a-plugin-platform` 切出并叠加于其契约之上。来源：已批准插件计划的
Track A 阶段 2，收窄到发送路径（`message.decode` 随其供给的阅读横幅移
至 SP3c）。

**范围。** 每次提交发起的发送在进入引擎队列之前经过所有已注册的
`before_send` 处理器；每份草拟渲染出的正文在闸门之前经过所有已注册的
`composer.transform` 处理器。被处理器阻断的发送永不入队：它以待决发送
的形态留在发件箱界面中，点名插件与原因，由自动保存已持久化的草稿承
载。不在本切片：`message.decode` 与其阅读窗格横幅（SP3c）；插件到宿主
方向的调用（尚无消费者）；按次发送审批 UX（分发切片的同意对话框）；对
处理器激活前已入队 op 的追溯过闸（引擎拥有队列，见下文记录）。

## D1：闸门是一个端口，在入队之前裁决

引擎拥有队列及其提交调度；astra-app 无法在 drain 内部否决一个 op。因此
闸门运行在执行权仍在应用手中的地方：每个提交臂中，草稿构建之后、
`submit_mail` 入队之前。新端口 `BeforeSendGate` 接收已构建的草拟（账
户、收件人、主题、两种正文），回答一个裁决：`Allow`、
`PromptUser { plugin, reason }` 或 `Block { plugin, reason }`。宿主（桌
面端）在任一已激活插件服务 `before_send` 时安装它；未安装时提交零开
销。处理器激活前已入队的 op 不做追溯过闸：引擎拥有它们的调度，这一限
制如实记录在已知缺口中。

## D2：待决发送留在发件箱界面，而非引擎队列

被阻断（或超时、或变换失败）的发送永不入队，因此任何 drain 都不可能泄
漏它：没有明文回退是由构造保证的。该发送以**待决行**的形态立在
`SendingSnapshot` 中（`held: Vec<HeldSend>`，每行点名插件、原因与模
式），草拟仍是已保存的草稿，退出不丢任何东西。闸门中途退出不会入队任
何东西；再次发送会重新运行所有处理器——这正是计划对入队前闸门的"重
启重跑"规则。待决行提供重试（对仍持有的草拟重跑闸门）与撤回（待决条
目消失，草稿留在草稿箱）。`AwaitingPluginVerdict` 是同一行的在途形
态：从闸门开始的第一秒就可见，点名正在等待的插件，裁决到来时转为待决
或消失。

## D3：模式是声明的，block 是默认

manifest 新增 `before_send_mode`：`block`、`soft_block` 或
`prompt_user`（声明 `before_send` 时必填）。`block` 在处理器批准前不能
发送，处理器不可用即阻断（默认值，对应 kylins 的无明文回退）。
`soft_block` 违规时阻断，但 worker 不可用时放行。`prompt_user` 把处理器
的理由呈现为 Send Anyway / Deny 决定，用户经 intent 作答；答案绝不静默
记忆。超时沿用 Outlook 的形态：待决行从第一秒起点名所等待的插件（约 5
秒的提示），约 5 分钟的上限对 block 模式失败关闭、对 soft-block 模式失
败开放。每个插件每份草拟一个处理器，自动激活需 `admin` 授权（集中部署
规则），桌面闸门在调用前检查。

## D4：变换失败关闭，先于闸门

`composer.transform` 处理器（`compose_edit` 层级）在草稿构建之后、闸门
之前运行：返回的 HTML 与纯文本腿替换渲染结果。出错或不可用的变换**不
会**发送未变换的邮件（那正是 kylins 有意拒绝的明文回退）：该发送以待
决形式停留，原因点名变换的名字，与闸门阻断行完全同构。变换按
manifest 顺序运行，每个看到的是上一个的输出。

## D5：桌面闸门在注册表上聚合

`client/desktop/src/plugin/gate.rs` 在注册表的已激活 worker 上实现两个
端口：对每个服务中的插件发起 `object_call`（`before_send` /
`composer.transform`），应用按插件的超时与其声明的模式，把各答案折叠成
应用所要的单一裁决（block 优先于 prompt 优先于 allow；首个 block 赢得
理由）。在上限内始终未答的插件对该次调用视为不可用。审批作答经新命令
`plugin_gate_answer` 回传，携带待决 id 与用户选择。

## D6：证明

单元红灯钉住 astra-app 的每条裁决路径（被阻断者永不入队、待决行点名插
件、prompt 作答后恢复或丢弃、变换顺序与失败关闭、未装闸门零开销）。桌
面闸门的测试经 worker 宿主的自定义 spawn 路径，在进程内 duplex 流上驱
动真实的 echo 插件（该路径正为此而存在），echo 对 `before_send` 答
allow、对变换回显。实机证明走 docker harness：受控 live 套件中的脚本化
否决闸门证明 astra1 的发送在否决解除前到不了 astra2。计划要求的 stub
闸门冒烟即 echo 驱动的桌面测试加这条 live 否决。

## 已记录的已知缺口，不隐藏

- 在 `before_send` 处理器激活前已入队的 op 不做追溯过闸；drain 内的逐
  op 扣留需要当前钉定版本引擎不具备的支持。
- 待决行是会话状态；其背后的草稿是持久的，待决条目经重新发送重建。
- 插件主动发起的调用（worker 自行读取 AOM）尚无 envelope；本切片所需
  的调用都是宿主发起的，该缺口今天零成本，在有消费者时落地。
- 5 秒"耗时较长"提示即待决行本身从第一秒起点名所等待的插件；独立的
  计时横幅是润色，暂缓。
- `message.decode` 与其横幅属于 SP3c；渲染插件来源横幅的 UI 描述符模
  型随之一同落地。
