# 邀请：Astra Mail 契约

**范围。** 邀请邮件到达之后发生什么：阅读正文上方的卡片、决定卡片
是否出现的两个条件、没有 RFC 会搬上日历的存储副本、答复及其路线、
占位与过期、以及带提问的邮件回复回退。对每一个交付阅读窗格或日历的
表面都有约束力。实质移植自 mail-calendar 的 `invitations.md`，按
Astra Mail 今日交付的范围裁剪；缺口在文末记录，绝不静默。

**原则。** *邀请是别人拥有的会议。* 客户端绝不发明会议，绝不答复两
次，绝不让用户以为答复已送达而其实没有。

## 两条件门

一封邮件只有在两件事同时成立时才渲染邀请卡片：邮件携带引擎 hardened
解析器接受的 iTIP 调度部件（带解析器可读 `METHOD` 的 `text/calendar`
正文；没有 METHOD 的对象不是调度对象），**且**本账户是邀请点名的参
会人，经邮件的送达地址（`Delivered-To` 等）匹配，所以别名无需任何配
置。组织者自己的会议副本不渲染卡片。

该门把可操作的对象分成四类：

| 类型 | 含义 | 操作 |
|---|---|---|
| `rsvp` | 欠一个答复且本账户是欠方 | 接受、待定、拒绝 |
| `cancelled` | 组织者取消了会议 | 无 |
| `informational` | 详情而已，本账户无需答复 | 无 |
| `superseded` | 日历持有该会议的更新版本 | 无 |

卡片携带类型、本账户当前的参与状态、会议标题与组织者地址；被取代的
卡片声明已过期并停止提供答复。

## 存储副本

没有 RFC 会把邀请搬进日历；客户端从邀请自身的字节存储它，键关联来源
邮件（RFC 6638 §3.2.2 的存储副本模型）。会调度的服务器存自己的副
本，存储的那份跟随服务器；仅以邮件送达的邀请在答复时落到日历。

未答复的会议在网格、月视图与议程上画为占位，与已接受的区分。已拒绝
的会议离开日历；邀请邮件是回去的路径。

## 过期判定

存储副本的 `SEQUENCE` 与邮件的相比较决定新旧：日历已越过的序列使邮
件被取代，卡片声明这一点而不是提供会重写新状态的答复。

## 答复及其路线

`RespondToInvitation` 回答接受、待定或拒绝，可选附一条成为回复
`COMMENT` 的便条。答复走哪条路线由账户的日历能力决定，绝不假设：

- **服务器调度**（RFC 6638）：存下答复*就是*发送它。回执不报告答复
  的送达，客户端也不再发第二份回复，因为组织者会听到两次。
- **服务器不肯发**：答复被存储，一封邮件 iMIP 回复经引擎的持久发件
  箱提交，与发出的邮件完全一样：先入队再问服务器，绝不发两次，发不
  出去随答复的失败一并撤回。

## 答复提示

当邮件回退的提交失败，或宣称支持调度的服务器报告回复未送达时，用
平实的语言告知用户并改供邮件。提示点名会议与组织者（邮件将到达的收
件人），显示它将携带的答复与 RSVP 时给出的便条，并提供发送或不发
送。该选择可按账户记住：Always 不再询问直接寄出每份回退回复，
Never 保持沉默，默认是 Ask。被记住的选择经同一路由表处理之后的每次
失败；不携带任何过期状态，回复在发送时从存储重新推导。

## 已知缺口

- **卡片不显示参会人名单、冲突或当日网格**；它携带类型、参与状态、
  标题与组织者。
- **邀请自带的 .ics 部件**尚未从附件列表中抑制；真正附加的日历文件
  仍显示。
- **尚无表面编写 dav 节**（联系人契约的缺口列表），所以存储账户必须
  已带有该节，宿主的启动拨号才能填充卡片的日历侧状态。
