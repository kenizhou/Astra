# AI 回信：Astra Mail 契约

**范围。** A1 基础上的 A2 回信起草能力：草稿池及其生成、浮现门与智能回复
条、带缓存的摘要、按账户的写作风格档案、暴露它们的宿主命令与 CLI 读取，
以及钉住其提示词的评测。约束每一个交付其中任一能力的界面（目前是桌面宿主、
网页阅读窗格与 `astra-cli`）。

**原则。** *AI 起草；人决定并发送。* 起草出的回复是读者可以接受、编辑或
关掉的建议；这里没有任何东西会发送邮件。接受一条回复条会按 SP2f 的回复
流程打开预填好的编写器，发送本身仍和从前一样是人的动作，走持久发件箱。
回复条绝不自动发送，任何 agent 动词也够不到回信路径：CLI 只读草稿池并
拒绝生成（见下面的模型规则）。

## 草稿池

每次为一条邮件尝试生成回复就落一行（`ai.sqlite` 迁移 `0004`）：邮件的
账户与键、起草的回复及其置信度、生成回合的关联 id、库自盖的创建时间。
**跳过行**（回复与置信度为空）记录一次失败或不可解析的生成：失败被记住，
之后的打开不再重试，也绝不打扰阅读界面。草稿池就是生成跟踪：只有池中
无行的邮件才会在被打开时武装一次生成，跳过行也算已试。

打开邮件（OpenMessage）会武装一次后台生成；宿主为应用生命周期运行的
driver future（`drive_reply_drafting`，收件扫描 driver 的接缝）取走武装，
模型延迟不落在打开自身的路径上。打开铸造阅读回合的关联 id，生成的账本行
随它走；每个宿主拉取（回复条、摘要、风格）各自铸造。

## 生成

一份带版本的提示词（`DRAFT_REPLY_PROMPT_VERSION`，draft 层）、一次结构化
补全 `{reply, confidence}`、一次严格解析加一次 `repair_json` 恢复、无论
成败各落一行池。置信度是封闭集（`low`、`medium`、`high`），以其固定分值
（0.3、0.6、1.0）入库；未知置信度词让整次解析失败并记录跳过行，绝不猜。

上下文收集器像每份 Astra 提示词一样把两半分开：指令、输出策略、风格笔记
与账户的知识上下文行走受信半区，笔记与知识行明确标注为数据（基于非受信
邮件的模型衍生文本绝不能冒充指令）；每封线程邮件各自进入非受信包裹。线程
按引擎线程读返回的新者在前，渲染旧者在前、原文最后，让模型回答读者正打开
的邮件。上限：`THREAD_HISTORY_LIMIT`（8）条较早成员、每封
`THREAD_BODY_CAP`（2000）字符（带截断标记），原文包括在内，知识上下文
另有自己的十条上限（辅助模型的读取）。

## 浮现门

一条入池草稿浮现为回复条，当且仅当其置信度越过 `CHIP_CONFIDENCE_FLOOR`
（0.6，medium 与 high 越过，low 留在池中）**且**二元判定器
（`JudgeDraftSurface`，nano 层）对值得浮现的问题回答 Yes：这条起草回复
是不是用户可以直接发出的真正有用的回复，而不是凑数？问题的措辞让 Yes
是正极；弃权的判定器（含安全默认）藏起回复条，什么也不损失：该行留在
池中，可经 CLI 查询。**关闭标记**（`0006`，按邮件为键）在任何判定调用
之前被查阅：被关闭的邮件绝不再花一次 nano 调用。跳过行、空白回复、
低于下限的草稿根本到不了判定器。

`GATE_JUDGE_VERSION` 为浮现门的提示词两半做版本：问题的措辞与上下文
半区的形状。今天上下文只携带起草回复本身，按非受信包裹；原文**不**进入
判定上下文。这条边界就是升级条件：`surface_question` 的措辞、或上下文
半区携带的内容（比如把原文放进去）任何变化，都要升级该常量并重跑门
评测。

## 回复条与关闭

阅读窗格至多显示 `CHIP_LIMIT`（2）条回复，每条是一行预览
（`CHIP_PREVIEW_CAP` 80 字符，空白折叠，截断加 `...`），旁边是它代表的
整条回复。窗格在打开时、以及 driver 的 sink 在有行落下时发出的
`draft_pool` 事件上拉取回复条。**接受**按 SP2f 回复流程分发，起草回复
成为文档的开头段落（`compose_from_draft`：回复自身的预填、收件人、主题、
线程头，草稿段落位于引用原文之上，正是恢复路径的文档约定）；编写器作为
回复打开，人照常编辑发送。**关闭**记录标记并永久藏起该邮件的回复条；
写入幂等，拉取先查阅它。

## 摘要缓存

`summarise(message)` 以 Summarise 用例（default 层，
`SUMMARISE_PROMPT_VERSION`）处理非受信包裹的邮件，并把答案缓存在
`0005`，键为邮件身份加正文的哈希（标准哈希器对纯文本的十六个十六进制
字符）。之后对同一正文的摘要从缓存应答，**无**网络调用；正文变了哈希
就不同，重新摘要。失败方向是假未命中，绝不是过期命中。缓存是优化，
不是门：缓存不上的摘要照样应答。

**键不含提示词版本。** 缓存键携带正文哈希，不含
`SUMMARISE_PROMPT_VERSION`：升级摘要提示词不会使已缓存的摘要失效，旧
摘要继续应答直到正文变化。真需要时给行加版本列即可关闭；此处记录为
有意的取舍，不是疏漏。

## 风格档案

`StyleInfer`（economy 层，`STYLE_PROMPT_VERSION`）从至多
`STYLE_SAMPLE_LIMIT`（20）封最近的已发邮件构建按账户的风格笔记，每封
正文上限 `STYLE_SAMPLE_BODY_CAP`（2000）字符，每封样本非受信包裹（用户
自己的邮件也是邮件；笔记本身是模型衍生文本，在起草提示词中作为数据）。
笔记存于 `0004` 的兄弟表 `style_profiles`（账户主键、笔记、`built_at`），
没有笔记时起草提示词完全省略。

重建只在需求驱动下进行（无后台定时器）：超过
`STYLE_PROFILE_MAX_AGE_SECS`（一天）、没有档案、或强制重建时才再推断；
新档案直接从库应答，不花调用。没有已发邮件就没有档案（空文件夹绝不抹掉
已建档案），失败或不可解析的推断回退到已存笔记：过时的笔记好过没有。
已发样本来自新者窗口行读（`STYLE_SENT_WINDOW`，200 封）按 Sent 角色过滤，
因为钉住的引擎版本不提供按邮箱范围的邮件读；窗口对 20 个样本的上限足够
宽，每日上限也约束了收集频率。

**重建拒绝（记录在案的规范偏差）。** 规格 D5/D6 的句子"一个 CLI 动词
`ai style rebuild`（唯一的可变动词，`--preview` 描述重建）"不交付。既定
规则（CLI 绝不拨模型）胜出：重建是对已发邮件的一次 StyleInfer 补全，
`rules create` 的 agent 组稿并行不成立，因为 agent 提供的笔记会绕过已发
邮件的 grounding，可能污染档案。CLI 以拒绝（退出码 3）交付该拼写，指明
模型规则并指向应用。应用侧的重建路径就是上面的需求驱动读取：每日上限
过去后的下一个起草回合或风格读取会推断新笔记。也没有显式的
`style_rebuild` 宿主命令，因为没有界面调用它（A2 的 UI 没有重建按钮）；
需要它的界面落地时它随之而来，CLI 的指引也在那个变更里点名它。

## 人的发送规则，重述

本切片不发送任何东西。回复条预填一封由人编辑、经持久发件箱发出的回复；
摘要与风格路径只读取和推断，绝不写邮件；agent 的 CLI 动词读取存储表并
拒绝唯一的模型类拼写（`ai style rebuild`，退出码 3，账本行记录拒绝）。
每次模型调用（判定或补全）都在回合关联 id 下落 `llm_calls` 行，A1 的
可追溯契约不变。

## 评测钉子与实证

三份提示词经同一挂具（`evals/` 夹具、接缝参数驱动）钉住常量：
`DRAFT_REPLY_PROMPT_VERSION`（起草形状、修复路径、未知置信度跳过）、
`SUMMARISE_PROMPT_VERSION`（解析出的摘要、不可解析错误、以及从一个
脚本答案服务两次读取的缓存钉）、`GATE_JUDGE_VERSION`（有用回复浮现、
no 与弃权默认隐藏、低于下限与已关闭的不花费钉、以及受 live 门控的
有用回复场景）。离线电池在 CI 里跑；live 场景随桌面宿主的 live 评测套件
在 `ASTRA_LIVE_LLM` 门下运行。

受门控的 live 套件（`client/desktop/src/ai/live_replies_tests.rs`，
`ASTRA_LIVE_LLM=1` 加 `ASTRA_LIVE_HARNESS=1`，对运行中的 Stalwart
harness，逐个测试串行）以真实接缝证明各阶段：为播种的富笔记起草一条
真实回复（池行、账本成本、线程历史上限对照真实线程的健全性检查）、
在该真实池上端到端拉取回复条（恰在置信度下限被越过时花费一次判定）、
一条钉住的有用回复获得真实的门判定、摘要两次应答只花一次网络调用
（账本行数即证明）、以及从证明自行发送所归档的 Sent 副本现场推断风格
笔记，每日上限不再花第二次调用、Sent 窗口覆盖整个同步集。

## 已知缺口

- **回信起草 driver 周围没有 panic 隔离。** 与收件扫描相同的遗留：driver
  内的 panic 会带走 driver，重启前之后的打开不再起草。武装草稿的打开
  本身受保护（生成跑在 driver 自己的 future 上），损失只是后台起草。
- **Sent 样本在每日上限决断之前收集。** `style_note` 先收集 Sent 窗口并
  取至多二十个正文，档案 getter 的每日上限才说不需要推断，于是被上限
  挡下的回合白白花了收集（引擎读取，无模型调用）。收集真值得在意时把
  检查前移。
- **摘要缓存键不含提示词版本。** 见缓存一节；旧摘要跨提示词升级继续
  应答，直到正文变化。
- **仅 HTML 的邮件只凭主题与发件人起草。** A1 遗留（只用纯文本正文）：
  正文仅 HTML 的邮件在起草上下文中正文为空。harness 的富笔记正是这个
  形状，live 套件照样起草它；纯文本提取随需要它的阶段落地。
- **每次回复条拉取都重新判定。** 门不缓存判定：每次拉取（打开、随后
  池落地）对每条越过下限的行花一次 nano 判定调用。花销真成问题时，按
  池行 id 键控的判定缓存可以合并它们。
- **没有显式的重建入口。** 重建路径是需求驱动的每日上限读取；没有宿主
  命令或按钮强制重建（上面的偏差记录了它的形状）。
- **风格笔记只随起草它的账户走。** 档案按账户，草稿读自己账户的笔记；
  刻意不跨账户共享。
