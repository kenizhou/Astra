# AI 规则：Astra Mail 契约

**范围。** SPA0 骨架上的 A1 AI 能力：规则模型（生成、匹配、确定性执行）、
每次刷新后运行规则的收件扫描、发件人分类、冷邮件判定、生效的 DLP 门，以及
钉住每份提示词的评测挂具。约束每一个交付其中任一能力的界面（目前是桌面宿主
与 `astra-cli`）；二元判定原语本身是二元判定规范的契约，此处只引用，不重述。

**原则。** *模型判定与起草；确定性核心执行。* 模型可以回答一个比特（一次
匹配、一个判定）或一个结构化值（一个类别、一条规则），绝不直接执行动作。
动作走应用自身的写路径，带审计记录，共用扫描的一个关联 id；不确定的模型
总是解析到表中指明的安全默认值。

## 规则模型

一条规则四个字段：短名称、一句自然语言条件、封闭的动作列表、启用标志。
规则存在 `ai.sqlite`（迁移 `0002`），与账本、结果、CLI 共用的那一个库。

动作集是封闭的：`mark_read` 与 `set_flagged`，即 A1 交付的确定性、可逆的
一对。未知的动作词在规则越过每个边界处都被响亮拒绝：生成中命名则整体失败，
存储的载荷携带则加载失败，CLI 的动词在解析处拒绝。更宽的动作集（文件夹、
草稿回复）随其切片到来，以增量方式扩展封闭集，并把绑定每种拼写的钉子放在
同一个变更里。

**封闭集刻意拼写两遍。** 应用层的 `Action::ALL` 与 CLI 的 `CLOSED_ACTIONS`
在两个互不依赖的 crate 里携带同样的线词（CLI 只依赖 `astra-ai`，不依赖
`astra-app`）。两者各有自己的测试钉住；任一个词的变更都要带着测试在同一个
变更里落进两处。这处重复是 CLI 依赖下限的诚实代价，不是疏漏。

### 生成

`prompt_to_rules(text)` 把平实的英文指令转成规则：一份带版本的提示词
（`RULES_PROMPT_VERSION`），一次 default 层的补全，一次严格解析，模型把
JSON 包进散文时走一次 `repair_json` 恢复。指令文本由用户撰写，不加包装直接
进入（受信，生成提示词自身的契约）；邮件内容根本不进入这份提示词。生成的
规则带新铸造的 id、默认启用；存储是调用方的一步。

**CLI 生成接缝。** `astra-cli rules create` 接受显式的条件句子，不做任何
生成：CLI 不持有模型客户端，也永远不会有（离线提供商契约；它不拨任何服务
器）。驱动 CLI 的 agent 用自己的模型自行撰写条件，动词照单存储。经由后台
客户端的生成在桌面宿主里，客户端在启动时装配。

### 匹配

一条规则对一封邮件是一次 economy 层的 `JudgeRuleMatch` 调用：条件句子作为
数据走受信的问题半边，邮件（发件人、主题、按 `MATCH_CONTEXT_BODY_CAP`
字符截断并带截断标记的正文）走宿主用加固围栏包住的上下文半边，因此邮件
永远无法冒充指令，条件也无法冒充邮件。问题的措辞让 `Yes` 是正极（匹配）；
弃权的判定解析为**不匹配**，规则不运行。安全默认表的答案上不执行任何东西：
确定性动作需要正向匹配。

### 执行

`Yes` 判定通过应用既有的写路径执行规则的动作（标已读、加星标），在扫描的
关联 id 下审计，每个动作与界面自身菜单一样幂等且可逆。模型不执行任何东西；
它只是回答了条件是否成立。

## 收件扫描

每次刷新重建之后，应用武装一次有界扫描；宿主运行的驱动 future（草稿自动
保存驱动乘坐的同一接缝）把它从刷新自身的路径上接走，模型延迟绝不落在用户
请求的刷新上。一次扫描铸造一个关联 id，读取启用的规则，审判最新的、此前
扫描未审判过的未读邮件头部（每次至多 `PASS_MESSAGE_LIMIT` 封，取自最新优先
的候选窗口；已读追踪通过结果行本身持久化，重启不重复审判）。

每个候选先过 DLP 门，再依次跑各阶段：规则匹配（每条启用规则一次判定调用）、
分类、冷判定。每个判定落在迁移 `0003`（`ai_results`：邮件账户与键、阶段、
判定对象为规则时的规则 id、判定词、类别）之下，共用扫描的关联 id；每次模型
尝试在旁边落它的 `llm_calls` 行。失败记日志、扫描继续；扫描做的任何事都
不得使武装它的刷新失败。只有宿主装配了 AI bundle（后台客户端上的两个接缝、
DLP 策略、那一个库）扫描才运行；没有则武装是空操作，驱动继续睡眠。

## 分类

每封邮件一次结构化补全（default 层，`CATEGORISE_PROMPT_VERSION` 版本化），
把它归入五个封闭词之一：`primary`（手写的个人邮件）、`newsletter`（订阅或
可退订的定期群发）、`receipt`（交易记录、账单、物流通知）、`notification`
（动作或日程触发的自动服务通知）、`cold`（推销东西的未经请求的联络）。分类
法与动作集一样封闭：命名其他任何词的补全使其分类失败，阶段把自己记成
`skipped`，绝不猜测。类别落进结果行；A1 尚无界面消费它（徽章随 A2 到来）。

## 冷判定

每封邮件一次 `JudgeColdEmail` 判定调用（nano 层）：这是否来自与收件人没有
既往关系的发件人的未经请求冷联络？问题措辞让 `Yes` 是冷极，安全默认是
**No，不冷**：不确定的判定原样放着邮件。A1 不对该判定执行任何东西；它被
记录（结果行的判定词，表作答时为 `abstain_default`），由 `astra-cli ai
cold` 读回。凭掷硬币搬动邮件比放着更糟；冷邮件可能换来的动作随之后的切片
与它自己的契约到来。

## 安全默认值，引用

每个判定用例在 `SAFE_DEFAULTS`（`astra-ai`）里预先声明弃权默认值，由两张网
守住：`safe_default` 的穷尽匹配在用例缺行时编译失败，运行时的钉测试逐字守
住表中的行。该表、其理由、以及边界（判定只门控用户体验，绝不门控
授权；权限桥与发送拒绝保持确定性）是二元判定规范的契约：
`docs/superpowers/specs/2026-10-10-binary-judge-design.md`。A1 的行：冷 ->
不冷，规则匹配 -> 不匹配，评测判定 -> 失败。花费守卫
（`ASTRA_LLM_NANO_BUDGET_MICROS`，每次判定调用前对照账本近一周 nano 聚合
检查；超限时安全默认作答、无网络调用、一行 `budget-skipped`）同样是该规范
的，照其钉住的交付。

## DLP：每份携带邮件的提示词前的门

`ASTRA_DLP` 为整个扫描选一种姿态，启动时读一次：`allow`（默认）原样放行，
`redact` 在进入任何提示词前遮蔽敏感片段，`block` 直接拒绝该邮件的 AI 阶段
（一行 `dlp` 结果行、判定 `blocked`、不花任何接缝调用）。该门按邮件、按字段
（发件人名、发件人地址、主题、正文）在构建任何阶段提示词之前应用。

畸形的值在启动时响亮地使扫描的武装失败（一条点名变量与可接受词的错误日志，
且不装配 AI bundle）：错误配置的策略绝不静默当作 allow。

`redact` 遮蔽邮件地址、电话形状的数字串（由分隔符缺口连接的 7 到 15 位数字）、
以及长数字串（无论有无分隔符的十二位及以上），每个字符一个遮蔽字符，布局
得以保留。启发式对死角是诚实的，`evals/` 下的评测夹具钉住边界，包括两个
有记录的未遮蔽死角：紧随 CJK 全角标点的地址会把下一个词粘进 TLD 而保持未
遮蔽；TLD 携带非 ASCII 字节的地址未过字母检查而保持未遮蔽。两者记录为死角
而非修复；遮蔽之网只在有夹具钉住加宽后形状时才加宽。

## 评测挂具与版本钉

场景夹具存于 `evals/`（每场景一个 JSON：feature、mode、其提示词文本写作时
所依据的流水线常量值、inputs、expected）。离线场景在 CI 里以注入的夹具答案
作为普通测试运行；live 场景（判定背书、依赖模型答案）只在
`ASTRA_LIVE_LLM=1` 下由桌面宿主的 live 套件通过同一接缝参数 drive 运行。
运行器与夹具紧邻它们所锻炼的接缝，评测失败即点名移动了的契约。

每份携带提示词的场景钉住它写作时所依据的流水线常量
（`RULES_PROMPT_VERSION`、`CATEGORISE_PROMPT_VERSION`、`COLD_JUDGE_VERSION`、
`RULES_MATCH_VERSION`、`JUDGE_TEMPLATES_VERSION`），离线全套断言每个钉等于
构建值：不改常量、或改了常量不重跑并刷新场景，离线套件即失败。这执行的
正是 AI 规则：AI 行为变更要求同一变更内的评测运行与流水线版本提升。

**账本中的 `JUDGE_TEMPLATES_VERSION`：现裁定不做。** 把提示词版本放进每行
`llm_calls` 需要账本的模式变更，且每个写者（宿主客户端、sidecar 中继、CLI）
要在一个变更里一起动；版本钉之网已使静默的模板提升在离线失败，常量与它
版本的模板同处。裁定在此作为已知缺口记录；只有调试需求真正要求逐行提示词
溯源时该列才到来。

## 实机证明

带门的 live 套件（`client/desktop/src/ai/live_tests.rs`，在
`ASTRA_LIVE_LLM=1` 加连接环境、harness 测试再加 `ASTRA_LIVE_HARNESS=1` 对
运行中的 Stalwart harness 下运行）以真实接缝证明各阶段：生成可解析、分类在
封闭集内决定、一次真实判定调用为真正落种的 harness 笔记在 `0003` 与账本中
落判定、token 计数与结局落进 `llm_calls`（合理界，绝不精确钉）、live 模式
评测场景对模型答案成立、以及一次完整刷新端到端驱动扫描、全部阶段行共用一个
关联 id。

**一个端点怪癖，已见已录。** 经验证端点在 anthropic 兼容线后是推理模型：其
`content` 数组在文本块之前携带 `thinking` 块（解析器取第一个文本块，thinking
无害随行），而 thinking 耗尽整个 `max_tokens` 预算的响应根本不带文本块。客户
端对该无文本 2xx 的归类与任何畸形信封相同：可重试、推进链；判定器折叠进安全
默认；单条目链以不可达上浮。不为它设特例，这是设计：契约在归类，不在端点的
名字。

## 已知缺口

- **只有 html 的邮件以空正文进入各阶段。** 扫描用引擎的纯文本正文构建上下文；
  正文只有 html 的邮件（如 harness 的富笔记）把主题与发件人带进提示词，但不
  带正文文本。阅读界面看到 html；AI 阶段看不到。需要时在扫描处加纯文本提取，
  随其自有夹具落地。
- **收件扫描驱动没有 panic 隔离。** 驱动逐次内联运行扫描：一次扫描 panic 会
  带倒驱动，重启之前不再有后续扫描。武装它的刷新仍然受保护（扫描跑在驱动
  自己的 future 上，不在刷新的路径上），损失的只是 AI 扫描。
- **无法解析的头部候选消耗扫描注意力且不留行。** 扫描无法为其构建上下文的
  候选（账户已不在、邮件不再可解析、正文取不回）只以一条日志跳过；没有
  skipped-with-error 结果行记录它，于是每次后续扫描都在窗口头部再次遇上它。
  界本身今天不会被饿死（这类候选不计入 `PASS_MESSAGE_LIMIT`）；代价是重复的
  注意力，不是损失的容量。
- **单一全局关联持有者。** 扫描的关联干净地横跨自己的行，但 agent 中继的单
  一全局持有者与无会话请求的 `any_correlation` 归因仍是单会话约束（AI 地基
  已记录的缺口）；两个世界只在那一个账本文件里相遇。
- **`JUDGE_TEMPLATES_VERSION` 不是账本列。** 上文裁定不做；记录在此使缺口
  与其裁定同在。
- **遮蔽死角。** `evals/` 下两个未遮蔽夹具是文档而非修复；见 DLP 一节。
- **live 场景是小集合。** 交付三个 live 夹具（cold、match、categorise）；
  离线全套承载形状覆盖。扩充 live 集是评测内容变更，不是契约变更。
- **CLI 的封闭集重复。** 刻意拼写两遍；句子在上文规则模型一节。
