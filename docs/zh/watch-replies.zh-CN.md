# 关注回复：Astra Mail 契约

**范围。** 关注一个会话的首条回复：关注一个会话，落地的首条回复会触发
一条「Reply received」通知并清除该关注（一次性）。对每一个交付该动词的表面
都有约束力。引擎没有关注概念，因此这是一个宿主/核心特性：一个设备本地的
关注存储、一个 pass 后到达检查、以及一个回复通知事件。不改引擎。缺口在
文末记录，绝不静默。

**原则（锁定的 kylins 参考红线）。** *关注绝不移动邮件，也不拥有任何引擎
状态。* 关注是一个普通的成员标记，从设置起直到首条回复将其清除。它不向
引擎写入任何东西：不移动、不加旗标、不建文件夹、不改关键字。检查只通过
引擎读取来解析会话。

## 关键：派生会话在合并时重新键控

派生会话以其合并分量中最小的自有 Message-ID 命名（引擎的 `store-sqlite`
派生线程化，内存存储与之镜像）。当一条回复持有的 Message-ID 比原始消息
更小时，引擎把两者合并为一个分量，并把每一个已存储成员重新键控到回复的
更小 id 上。因此，一个以设置时捕获的会话 id 为键、再与回复新解析出的会话
id 相匹配的关注，会错过大约一半的首条回复（在纯 IMAP 上，对随机
Message-ID 而言回复约有一半概率排在前面）。

因此关注携带一个代表性的 `member_key`：设置时捕获的被关注会话的一个稳定
提供商标键（一个链接，而非引擎状态）。检查在检查时通过引擎解析双方，
即批次的通知键以及每一个关注的成员键，每个账户一次 `mail_by_keys`，并以
解析后的结果相互匹配。成员行在重新键控后仍然存活（其会话 id 随分量一起
移动），因此双方始终命名当前的真实值。这一成员键重新解析在 v1 中交付，
而非后续；一个回归测试（回复的 Message-ID 排在原始消息之前）将其钉住，
门控的实机证明选择回复的 Message-ID 使其排在最前，从而在真实线路上证明
重新键控。

## 存储

新 crate `astra-watches` 持有成员关系（提醒存储的形状：一个互斥锁下的
rusqlite 连接、在事务中认领的嵌入式迁移、五秒忙超时、供测试用的内存
打开）。宿主在数据目录中打开 `watches.sqlite` 并安装到核心（categories
的安装形状，一个 `Mutex<Option<Arc<Store>>>` 槽；没有定时器，也没有
`AppState` 字段，因此丢弃顺序保持原样）。每个被关注会话一行：

- `account_id`，所属账户（新类型 `AccountId`）。
- `thread_id`，设置时解析出的会话 id，账户内该行的句柄（一个普通标识符，
  `ThreadRef` 约定）。
- `member_key`，设置时捕获的一个代表性提供商标键（新类型 `ProviderKey`），
  检查据以重新解析的链接。
- `created_at`，存储自身的时间戳。
- `PRIMARY KEY (account_id, thread_id)`。

方法为 `watch`（按键幂等 upsert，回答是否插入；重新关注保留既有行及其
成员链接）、`unwatch`（DELETE，回答是否移除；一次性消费正是骑在这个方法
上）、以及 `list`（跨账户按 rowid 顺序，供未来的设置表面使用）。没有到期
逻辑，也没有定时器：到达通道是唯一的触发器。身份无法解析的行被跳过，
绝不致使列表致命失败。存储是设备本地的：不跨设备漫游，CLI 也不共享它。

## 核心动词与 pass 后检查

`watch_thread(row)` 解析会话键（会话行直接用其 id，消息行通过一次引擎
读取，categories 的 `resolve_thread_key` 约定）并捕获一个代表性成员键：
会话行通过 `mail_on_threads` 读取其最新成员，消息行使用自己的键。它记录
标记并回答本次调用是否插入。不移动，不写引擎。`unwatch_thread(row)` 解析
相同的键并清除标记。`list_watches()` 回答每一个关注，按插入顺序。

`check_watched_replies(batch)` 是异步的 pass 后主体。`watch_replies_enabled`
偏好对其门控（关闭时回答为空且不消费任何东西）。它按账户对批次的通知键
分组，每个账户读取一次 `mail_by_keys`，涵盖批次键加关注成员键，把每一个
解析出的行映射到其会话键（解析出的会话 id，从未线程化时则为提供商标键），
并以解析后的结果相互匹配对每一个被回复命中的关注，它从首条匹配回复
构建一个 `NewMailNotice`（回复自身的账户、键、发件人、主题与预览，因此
点击打开照常工作），并通过 `unwatch` 消费该关注。即使多个关注命中同一条
回复，每条不同回复也只产生一条通知。失败开放：任何读取或存储失败都被
记录并跳过其账户，绝不致使 pass 或基础新邮件通知搁浅；成员键不再解析的
关注保持武装但沉默。

## 宿主钩子与回复通知

生产环境的 `HostDelivery::pass` 在 drain 之后运行检查（同步的
`NewMailQueue` 提交折叠保持不动），以 `notifications_enabled` 门控，并通过
`NotifyBridge::deliver_replies` 交付答案。检查骑在交付驱动器上，即唯一的
生产 drain。

`deliver_replies(batch, enabled)` 遵从 `notifications_enabled` 开关，每条
回复展示一条标题为「Reply received」的 OS 通知（正文为发件人与主题），并
在 `reply` 事件上发出 `NewMailBatch` 载荷（overflow 为零）。没有焦点抑制：
显式的用户请求在窗口聚焦时也会触发，启用开关是唯一的门（Astra 没有 DND
设置）。历史通道失败被记录，绝不抛出，因此不会抑制已经跨过的 OS 通知。
基础的「New mail」通知仍在其旁触发（两条公告，kylins 对齐）。web 的
`replyFlow` 与 `replyEvents` 把每一次落地记录进新邮件挂载所喂的同一个通知
历史；历史面板无需改动（条目携带账户与键，因此点击打开照常工作）。

## 表面

行菜单的「Watch replies」条目（单行；批量以理由禁用）在会话已被关注时
翻转为「Unwatch」。线路骑在 `services/watchReplies.ts` 上（绝不放入已达
上限的 `ipc.ts`）；一个 zustand 关注集合存储从 `watch_list` 播种，并在每次
切换时刷新，按账户与 id 键控（每个关注的会话 id 与代表性成员键，因此会话
行按其会话 id 解析，消息行按核心捕获的成员键解析）。桌面命令位于
`commands/watch_replies.rs` 子模块（`commands.rs` 已达上限），背后是一个
`WatchPort` 超特征（`CategoriesPort` 模式，每个 impl 的块在自己的子文件中）。
通用设置页携带一个 `watch_replies_enabled` 开关（默认开启，端到端沿用
`notifications_enabled` 模式）。

## 参考偏差，已升级

锁定的 kylins 参考仅在基础吐司触发时（在 DND/静音门之后）运行关注钩子，
并在那里消费。本切片转而遵循已交付的提醒契约：回复通知没有焦点抑制，
并在 drain 时消费，因此聚焦的窗口仍会诚实地消费。两者都是对参考的有意
偏差，在此及 PR 中升级，而非静默。参考的红线得到遵守：关注绝不移动邮件，
也不拥有任何引擎状态。

## 已知缺口

- **溢出折叠**：一个 pass 中超过五条合格到达里的回复会被折进溢出计数；
  其键绝不到达被 drain 的批次，因此检查错过它，关注保持武装直到下一个
  pass（让队列携带该 pass 的完整新键集合是升级路径）。
- **仅背景通道**：检查骑在交付驱动器上（唯一的生产 drain）；手动刷新的
  到达在下一个背景 pass 才被检查（基础新邮件通知的同样暴露）。
- **陈旧成员链接**：若代表性被关注消息被移动（IMAP 合成一个新键）或删除，
  关注便不再能解析；失败开放，关注保持武装但沉默（稍后处理的 Message-ID
  重新解析是升级路径）。
- **菜单标签按代表性成员解析**：不是被关注代表性成员的消息行，即使其会话
  已被关注，也读作未关注（会话行与代表性消息能正确解析）；行级关注徽章
  是升级路径。
- **设备本地**：不漫游，无 CLI/agent 动词，无徽章，无设置/调试列表（可选
  后续），无多选关注（kylins 对齐）。
