# 提供商 OAuth：Astra Mail 契约

**范围。** 浏览器登录在邮件提供商处如何运行，签发的令牌如何保管、
如何刷新：覆盖 Astra Mail 持有注册的提供商（Microsoft 365、Google），
以及完全依据标准发现的陌生服务器（RFC 9728、RFC 8414、RFC 7591）。
对每一个提供 OAuth 路径的表面、每一个消费它的账户类型都有约束力。
实质移植自 mail-calendar 的 `provider-oauth.md`，按 Astra Mail 今日交付
的基础裁剪；缺口在文末记录，绝不静默。

**原则。** *本应用是公共客户端：没有值得窃取的秘密，仅有的一件秘密
保存在 OS 密钥库里，登录在用户自己的浏览器会话中进行。* 下文的每条
规则都是把这句话变得可检验。

## 两个一半

OAuth 状态机按"什么可以纯测试、什么天然属于平台"来切分：

- `crates/astra-oauth`，纯的一半。PKCE 与 CSRF state 的铸造、令牌交换
  （精确的表单体、时钟偏移、已授予集合的写入规则）、Microsoft 与
  Google 的端点和范围表、授权拒绝的词汇表、传输 reach 划分，以及发现
  与注册链。不依赖引擎；每次网络调用都跑在注入的 HTTP 客户端上，该
  客户端构建于共享 TLS 策略（`engine_tls`）之上，所以 OAuth 信任的
  与同步信任的完全一致。
- `client/desktop/src/oauth`，宿主的一半。登录会话（通过注入的缝打开
  系统浏览器、捕获重定向、把原始 URL 原样交回：Microsoft 走深链
  scheme，Google 走一次性的回环监听器）、宿主
  `AccountCredentialStore` 端口之上的凭据事务，以及设置向导的登录
  命令及其类型化完成事件。

引擎对 OAuth 不可知：它只取一个不记名访问令牌，再无其他，所以令牌
的获取与刷新绝不越过 `engine-api`。

## 规则

1. **带 PKCE 的授权码，公共客户端。** 本应用是公共客户端；保护令牌
   交换的是 PKCE `code_verifier`（S256），由系统 CSPRNG 铸造。客户端
   id 不是秘密，可以内嵌。绝不内嵌任何机密秘密，只有一处有记录的例
   外：Google Desktop 客户端（回环流程）携带一个非机密的
   `client_secret`，Google 的令牌端点在代码交换与刷新两处都要求它；
   Google 自己的指南说它"显然不被当作秘密"。见规则 13。

2. **系统浏览器，绝不用应用内 WebView。** 登录在平台的系统浏览器会话
   中运行，而不是内嵌 WebView。这复用用户已有的浏览器登录（常常省去
   一次密码输入），并让应用置身凭据路径之外。会话刻意非临时：它要的
   就是共享的浏览器会话。桌面宿主上的浏览器是 OS 默认浏览器，经
   opener 支撑的缝打开。

3. **自定义 scheme 重定向，经 `state` 验证**（Microsoft 的流程；
   Google 的 Desktop 客户端类型不支持自定义 scheme，其流程经 Google
   节自有的回环重定向返回）。重定向回到应用自己的
   scheme（`com.kenizhou.astra`，即 `tauri.conf.json` 已携带的标识符），
   在深链块中与 `mailto` 一同注册；提供商配置使用的重定向 URI 是
   `com.kenizhou.astra://oauth`。捕获按同一 scheme 过滤，把原始回调
   URL 整体交给纯的一半；宿主绝不自己解析令牌。纯的一半拒绝 state
   与其铸造的不匹配的回调（可能是 CSRF）、缺少 code 的回调，并且对
   声明会发送（RFC 9207）的服务器，拒绝 `iss` 指向任何其他授权服务器
   的回调：这是混淆攻击的防线，而这样的服务器缺发 `iss` 本身就是失败
   而不是放行，因为被剥掉 `iss` 恰是那种攻击的产物。

4. **令牌只存在于 OS 密钥库。** 存储的账户凭据只携带刷新令牌这唯一
   的一件静态秘密；访问令牌按需铸造，绝不持久化。秘密类型在日志与
   调试输出中自我脱敏。存储是宿主的 OS 安全库（今日为 Windows 凭据
   管理器），与密码账户使用同一个库。

5. **凭据的生命周期是一个事务，而且它要作答。** 存储凭据的创建、替换
   与擦除都经由宿主 `AccountCredentialStore` 端口之上的一个事务进行，
   该端口只有 `persist` 与 `delete`。宿主拥有只有它能拥有的（加密、
   访问控制、存储条目）；下文的规则拥有"何时"。

   **事务放哪里与参考实现有意分歧。** mail-calendar 把事务放在它的
   core 里，遵循"core 拥有何时、宿主拥有何地"。Astra Mail 的事务在
   宿主一侧、包住端口，理由有三条，随模块一同记录：端口本身就是宿主
   的，应用 core 只通过 account-operations 缝看到它，而那个缝不暴露
   通用的 persist；应用 core 完全不携带 OAuth 类型，放在 core 的事务
   得先为一个直到提供商切片落地才存在的消费者拓宽 core 的表面；而
   账户新增流程本来就把自己持久化纪律放在宿主里（`add_account` 在
   拨号之后持久化，拒绝时回滚整个新增）。规则约束的是事务所在的
   任何地方。刷新锚点：Microsoft 账户的刷新路径（SP2m）持有这个事务
   并回答它的轮换，Google 账户（SP2n）经同一令牌源、同一事务拨号
   （其轮换写入是后备，见 Google 节）；令牌源听到的每一次轮换都落进
   拨号表的条目与存储，完成时的最终持久化读取条目，绝不读拨号前一刻
   解析的副本，所以拨号期间发生的轮换绝不会被撤销。

   **刷新不携带 scope，这条规则没得商量。** RFC 6749 第 6 节要求
   刷新请求的 scope 必须是已授予集合的子集，省略则精确表示原授予。
   因此发送构建的当前列表会弄坏在该列表变长之前签发的每一个授予：
   服务器回答 `invalid_scope`，整个账户停止工作，而不只是新范围对应
   的那个功能。省略是唯一不会过期的取值。scope 在授权请求上索取，
   那里才是同意发生的地方，也是重新登录所重跑的。纯的一半构造的
   刷新体一个 scope 参数也不带，逐字节如此。

   **授予携带什么以令牌响应为准，存储的副本跟随它。** 授予的 scope
   会被存储，使账户能做什么可以在启动时和离线时回答，但这个值是
   缓存：登录写入代码交换所命名的 scope（未命名时为请求集合，依据
   RFC 6749 第 5.1 节），此后每一个命名了不同集合的刷新都覆写它，
   包括收窄的，因为提供商处撤回的同意没有别的途径到达本应用。未
   命名的刷新不动它。未变化的集合不写，因为在某些宿主上每次刷新
   都写安全库就是一次提示。绝不为此读取访问令牌：Google 的不透明，
   Microsoft 的属于资源。

   **拒绝靠分类，绝不靠文本匹配。** 令牌端点的拒绝以分类作答：
   `Dead`（`invalid_grant`：已撤销或过期）、`Underscoped`
   （`invalid_scope`：仍有效但窄于本构建所需）、`Indeterminate`（其余
   一切，它对授予什么也没说）。前两者都需要同意，等待都不会恢复，
   所以调用方同等对待并停止重试；第三者绝不改变任何人对一次登录的
   判断，否则提供商的一个糟糕下午就会把人登出。向导的拒绝句子挂在
   分类词上，绝不在调用点匹配句子。

   **重放安全：把重放的刷新令牌当作盗窃的服务器会撤销整个授予。**
   现代授权服务器不只是拒绝被取代的刷新令牌；有些会直接撤销授予，
   账户即死，用户必须重新登录。Microsoft 与 Google 今天都宽容重放，
   这正是规则存在的原因：第一个接上的棘轮服务器绝不能是第一个丢
   账户的。四个一半共同守住这一点，分属两个切片：
   - **每账户同时只有一次刷新**，且刷新失败要与等待中的调用方共享，
     而不只是成功。序列化刷新并记住上次失败的令牌源随提供商切片
     （SP2m 先行）落地；它要消费的缝，即下面的传输 reach 划分，已经
     钉住。
   - **只有当请求可证明从未离开设备时，才允许用同一令牌重试失败。**
     传输划分回答这一点：`NotSent` 只在可证明处主张（DNS 失败、被拒
     的对端、失败的 TLS 握手），一切不明确都归 `MaybeProcessed`，
     刻意不对称，因为多谨慎一次的代价是延迟，反着错的代价是账户。
     各自带自己的冷却，且二者保持可重试，所以一个丢包绝不会把重新
     认证的提示推到用户面前。
   - **状态行之后死掉的响应是它自己的错误**，绝不归"传输"：请求到达
     了服务器，其处理器运行了，所出示的刷新令牌已被花掉。再出示旧
     令牌就是重放。
   - **能刷新的核心必须能够持久化。** 令牌源把存储当作必需输入，而
     不是指望宿主事后安装；没有存储接收的轮换是一枚服务器已经走过
     的存储令牌。它骑行的事务正是本规则 5 所命名的那个。

6. **依据标准发现，闭环失败。** 陌生服务器依次被问：它的 RFC 9728
   受保护资源元数据（来自 `WWW-Authenticate` 挑战的指针，否则用
   well-known 默认位置），其中命名授权服务器；该服务器的 RFC 8414
   元数据；及其声明提供的 RFC 7591 注册端点，它在全新的
   构建固定的 `SOFTWARE_ID` 之下铸造全新的客户端 id，安装绝不误归属。发现决定把用户
   的凭据发往哪里，所以它严格：每一跳都是 HTTPS（回环是唯一豁免，
   因为它从不抵达网络）、不跟随重定向（重定向把文档挪到签发者未命名
   的 URL）、元数据的 `issuer` 必须与所问的签发者匹配（RFC 8414
   第 3.3 节，正是它阻止被攻破的资源把本应用指向攻击者的令牌端点）、
   且必须声明 S256 PKCE。任何发现失败对调用方都是同一句话：这台
   服务器不提供可发现的 OAuth，改供手动秘密。

7. **`offline_access` 是必需的。** 没有它就没有刷新令牌，账户在设置
   一小时后坏掉。其执行点，即拒绝一次完成却没有带回刷新令牌的登录，
   是 Microsoft 完成路径的第一道门（SP2m）；规则是其余提供商继承的
   契约。Google 的对应物不是 scope：每次授权请求都带
   `access_type=offline` 加 `prompt=consent`，这样即使重复同意也
   会带回刷新令牌。

8. **在提供商门户里逐字符注册重定向 URI。** 它必须与客户端发送的
   完全一致。scheme 是应用自己的标识符；开发与发布版本的 scheme 拆分
   （参考实现需要它，因为打包与未打包构建按用户认领同一协议）在只有
   一个构建身份存在时没有对应物，出现第二个时再议。

9. **用 `login_hint` 定位要连接的账户。** 地址已知时，授权请求携带
   它作为 `login_hint`，对 Microsoft 还去掉 `prompt=select_account`，
   使提供商定位该账户而不是浏览器里已登录的另一个。没有提示时，
   Microsoft 收到 `prompt=select_account` 并显示选择器。浏览器里持有
   的账户与正在添加的不同时，这一点最要紧。

10. **失败或被拒绝的登录要呈现，绝不吞掉。** 提供商可能返回
    `access_denied`（同意被拒绝，或策略拦截了应用）；登录表面带着
    分类词展示拒绝，而不是什么都不做。一个默默无声的按钮是 bug。
    对账户接线还在等待的家族，诚实的推论是：JMAP 与 IMAP OAuth 的
    完成路径随其切片（SP2o、SP2v）落地，在此之前根本不提供这样的
    路径。

11. **在浏览器中被放弃的登录绝不卡死表面。** 关闭浏览器标签页无法
    探测，所以出路是显式的：会话持有一个在途槽位，流程尚存时新的
    begin 拒绝（表面永远带着取消：向导的取消按钮与关闭路径都会取回
    该对，被取消顶替的等待者停驻到下一个重定向或捕获关闭，绝不阻塞
    之后的流程：流程 id 检查把陌生的重定向交回通道，被顶替的等待者以
    Cancelled 作答且不发出任何事件）。无重定向的取消的代价：每个被
    放弃的流程停驻一个等待者，在下一次重定向或关机时释放。等待上限
    加取代的形态（mail-calendar 的等满）是记录在案的缺口，不是已交付
    行为。

12. **客户端注册在构建时注入，缺少注册的构建不提供该路径。** Google
    与 Microsoft 的客户端 id 只从一处进入产品，
    `astra_oauth::credentials`，用 `option_env!` 从环境读取：

    | 目标 | 变量 |
    |---|---|
    | 桌面 | `ASTRA_GOOGLE_DESKTOP_CLIENT_ID`、`ASTRA_GOOGLE_DESKTOP_CLIENT_SECRET` |
    | 所有目标 | `ASTRA_MS_CLIENT_ID` |

    这些是 Astra Mail 自己的注册，不是参考实现的：今天一件都没有
    发布，所以向导的 OAuth 提供对任何人都渲染不出来，检测也不推荐
    任何 OAuth 路径；源码构建是一台可用的开放标准邮件客户端，绝不
    是死按钮。缺省是受支持的构建而不是坏掉的构建。空白值等同缺省。
    参考实现的"拒绝无注册的发布构建"检查刻意尚未移植：它把缺失的
    注册变成发布构建的编译错误，而在注册存在之前这毫无意义，注册
    存在之日再议。

13. **范围集合点名它们的调用。** 登录按账户的用途索取范围，每个
    scope 都有调用点，那正是审批应用的管理员所读的。表格在纯的一半
    （`MICROSOFT_GRAPH_SCOPES`、`GOOGLE_SCOPES`）里，逐范围带理由；
    理由的形状：

    | 规则 | 原因 |
    |---|---|
    | Microsoft 每次都带 `offline_access`，Google 每次都带 `access_type=offline` | 刷新令牌本身（规则 7） |
    | `User.Read` / `userinfo.email` 恒有 | 账户自己的地址与姓名；没有谁读 ID 令牌，也不索取任何 OpenID Connect scope，因为每一条都会是同意界面上没有功能背书的一行 |
    | 邮件 scope（`Mail.ReadWrite`、`Mail.Send`；`mail.google.com`、`gmail.settings.basic`） | 邮件同步、每一项邮件写入与发送；发送绝不由邮件读取 scope 授予 |
    | 日历、联系人读写 | 账户的日历与卡片；联系人索取读写是因为产品会新增和编辑它们而绝不删除 |
    | 目录 scope（`User.ReadBasic.All`、`directory.readonly`） | 工作或学校账户上的同事；个人账户绝不索取，它没有目录 |
    | 用户无法自行同意的 scope 绝不索取 | 管理员把关的 scope 不是少一个能力，而是账户根本加不上，因为 `access_denied` 落在同意期间 |

    授予未给的用途不开放；存储的已授予集合缺少该 scope 就保持该用途
    关闭。Google 允许用户在同意界面取消勾选 scope，所以已授予集合会被
    读回并按提供商的拼法比较。变宽的集合只有重新登录才到达已有账户：
    刷新复用原授予。

## Microsoft 账户

这个地基之上的第一个账户类型（SP2m）：Microsoft 账户经浏览器流程登录，
其邮件与日历经由引擎的 Graph 适配器拨号，共享一个令牌源，它应得的表面
随之一并到达。本节按已交付的内容裁剪；其余在文末的已知缺口里携带。

**拨号。** 账户层的一个自由函数拨号 Microsoft 账户：邮件提供商，账户
列出的每个被同步文件夹一个，加上默认日历的提供商，附在邮件之后，
与 dav 账户的日历腿同形，宿主按能力圈定的选择会拾起它。启动、
登录的完成路径、重连都调用同一个函数，所以没有任何路径能对一个
Microsoft 账户打开什么产生分歧。两条腿共享同一个令牌源，所以一次拨号
至多铸造一个访问令牌。邮件腿是账户自己的：它的失败使拨号失败，死授予
以被拒绝的登录到达，绝不是断连。日历腿不是：拨号失败的日历（探针上
scope 被拒的 `403`，今日按服务器的 `ErrorAccessDenied` 措辞匹配，待
上游结构化分类）让账户站在邮件上，失败被携带给调用方呈现。刷新包装器
圈定它声明的能力：它不转发的能力就是账户没有的能力，服务器端草稿刻意
不声明（下面的记录在案的缺口）。

**地址查找。** 完成路径以刚铸造的访问令牌为账户命名：
`GET /me?$select=mail,userPrincipalName` 携带不记名令牌，SMTP 的
`mail` 优先，未设置 SMTP 地址时回退到登录名。命名不出地址的回复拒绝
该登录：提供商无法命名的账户不会成为账户，用户留在还在看着的设置
表面上。

**完成路径的顺序。** 账户的 id 由地址派生（`address@graph`），此后
一切都以它为键。令牌源在拨号**之前**注册进拨号表的条目：sink 读取
条目，所以拨号期间的轮换有处可落，下一次启动绝不出示已花掉的令牌。
最终持久化读取拨号表的条目，而不是拨号前一刻解析的副本，原因正是
如此。新 id 经事务的 `add` 持久化（存储拒绝时它自己回滚）；重新同意
经 `rotate`，绝不经 `add`，`add` 的回滚会删除一个站立账户的凭据。

**重新同意。** 为一个已站立的账户再次登录，保留授予之外存储的形状：
钉住的 id、dav 腿、已接受的证书。只有授予变化。重新同意上拨号失败把
站立条目原样放回；首次新增上拨号失败回滚整个注册，不留任何注册，存储
里也没有孤儿凭据。

**门规则。** 响应一个 scope 都没命名的授予在门口就被拒绝，任何注册
发生之前：没有任何权限的账户承载不了一个能力，早拒绝让用户留在设置
表面上，而不是走完一个以无法解释的文件夹列表拒绝告终的新增。执行者
是已授予集合缓存自己的话：响应命名时取响应的集合，未命名时取请求的
集合。

**表面。** 站立的拒绝状态是快照数据，不是事件：设置快照账户行上一个
增补的 `grant` 字段，经宿主的 account-info 缝取自启动拨号与登录完成
路径写入的映射。完成事件仍是向导的一次性通道；晚挂载的表面或重新启动
必须拉取站立状态，绝不捕获一次发射。写入者记录什么：启动拨号把死授予
分类成过期登录状态，对应它随后跳过的账户（该行是解释缺席的唯一表面，
即使应用并未持有该账户它也渲染，因为该行是提供重新授予的唯一表面）；
拨号通的日历探针回答需要重新授权时记录被扣留的日历；健康的拨号清除
原已站立的状态，因为应答了的拨号证明了站立状态是错的；被拒绝的完成
路径不记录任何东西，因为它的回滚规则让原已站立的一切保持原样。重连
横幅（被扣留的日历）与过期登录行（死授予，绝不误标为服务器断连）提供
同一个动作：重新运行登录，以该账户的地址为目标。

**范围集合，按已交付裁剪。** Microsoft 登录索取
`MICROSOFT_GRAPH_SCOPES`（纯的一半范围表中各用途组的并集）；已交付
的账户消费其中：

| Scope | 今日服务的用途 |
|---|---|
| `offline_access` | 刷新令牌；完成路径的门拒绝没有它的令牌集（规则 7） |
| `User.Read` | `/me` 地址查找 |
| `Mail.ReadWrite` | 邮件同步与每一项邮件写入；该组的需求 scope |
| `Mail.Send` | `POST /me/sendMail`；绝不由邮件读取 scope 授予 |
| `Calendars.ReadWrite` | 默认日历的读写 |
| `Contacts.ReadWrite` | 同意时索取；Graph 上的联系人腿随联系人切片落地 |
| `User.ReadBasic.All` | 同意时索取；同事目录随其切片落地 |

授予未给的用途不开放：已授予集合缓存在启动与离线时作答，被扣留的
日历 scope 经拨号的 `403` 探针呈现为重连状态，而不是崩溃。

**离线证明。** 引擎的 Graph 适配器不提供离线重放（其 live 测试以真实
访问令牌门控，其 fixtures 是给解析器的录制体），存储文档的令牌端点又
经 tenant 钉在真实的 Microsoft authority 上，所以证明在脚本化的回环
服务器上跑每一个离线可达的环节：真实的 `/me` 查找、真实的令牌源刷新、
单飞与经真实 sink 落进真实拨号表和凭据事务的轮换、完成路径的顺序、
启动的存储账户拨号，以及死授予的分类到达账户行。拨号缝本身在该证明
中是脚本化的；其令牌边界由账户层的拨号测试钉住。真实 Graph 上的实时
证明等待 Azure 注册，绝不伪造。

## Google 账户

这个地基之上的第二个账户类型（SP2n）：Google 账户经回环重定向的浏览器
流程登录，其邮件与日历经由引擎的 Google 适配器、在 Microsoft 账户所用
的同一个令牌源之后拨号，它应得的表面随之一并到达。本节按已交付的内容
裁剪；其余在文末的已知缺口里携带。

**回环重定向。** Google 的 Desktop 客户端类型不支持自定义 scheme，所以
规则 3 的重定向只属于 Microsoft：Google 流程回到
`http://127.0.0.1:<临时端口>/`，又因为端口本身就是重定向的一部分，
监听器在授权 URL 铸造**之前**绑定（流程绑定一个临时回环端口，以端口
写进重定向的模板配置重建其客户端，然后才打开浏览器）。监听器有界且
一次性：它站立数分钟，因为用户可以在同意页上停留任意久；不带回调形状
的请求（`POST`、探针）以 `400` 作答而监听器继续站立，因为浏览器可能在
重定向之前先探测；唯一一个解析通过的回调以写着要返回的应用名的关闭页
作答，套接字随即关闭（之后的连接被拒绝），只有那时捕获的 URL 才整体
交给纯的一半，`code`、`state` 与任何 `error` 的读取与深链捕获交回
URL 的方式完全一致。深链投递永远完不成回环流程：会话把每个提供商的
捕获路由到它自己的通道，所以 Google 流程等待期间 Microsoft 重定向到达
共享深链是陌生人的重定向，被交回并如此拒绝。注册在 Cloud Console
携带不带端口的回环前缀，它匹配任意端口（Google 的回环规则）。

**非机密秘密。** Google 的令牌端点在代码交换**与**刷新两处都要求
Desktop 客户端秘密，即便有 PKCE：规则 1 那处有记录的例外。该秘密不是
机密的（Google 自己的指南说它"显然不被当作秘密"），所以它随授予一并
持久化在 `[google]` 文档里：启动之后的刷新读文档并再次发送秘密，且它
绝不进日志。

**地址查找。** 已授予集合挑选为账户命名的端点。持有 `userinfo.email`
的授予（每次登录都索取它）读 `GET /oauth2/v3/userinfo` 取其 `email`
字段；没有它签发的授予经 Gmail 配置文件命名
（`GET /gmail/v1/users/me/profile`，其 `emailAddress` 字段），邮件
scope 覆盖该读取。命名不出地址的回复拒绝该登录：提供商无法命名的账户
不会成为账户，与 Microsoft 查找守的是同一道门。

**拨号。** 账户层的一个自由函数拨号 Google 账户，每条唤起它的路径
（启动、登录的完成路径、重连）都调用它，所以没有任何路径能对一个
Google 账户打开什么产生分歧。邮件半边是账户全局的：Gmail 没有按
文件夹的绑定，所以一个提供商服务整个账户，而 Graph 按每个被同步
文件夹拨号一个。日历按每个拨号日历的方式附在邮件之后。两条腿共享
同一个令牌源，所以一次拨号至多铸造一个访问令牌。没有 `403` 重授权
探针：Google 在登录时索取日历 scope，所以被拒绝的日历是拨号携带的
错误（邮件站立，失败为调用方点名），绝不是重新同意状态，重连横幅
保持仅限 Microsoft。

**完成路径的顺序与门规则。** 顺序与 Microsoft 的完全一致：id 由地址
派生（`address@google`），此后一切都以它为键；令牌源在拨号之前注册进
拨号表的条目；最终持久化读取条目而不是之前解析的副本；新 id 经事务的
`add` 持久化，重新同意经 `rotate`；重新同意保留授予之外存储的形状。
门前立着两道门，顺序如下：没有刷新令牌的令牌集**先于**地址读取被拒绝
（流程总是发送 `access_type=offline` + `prompt=consent`，所以缺失的
刷新令牌是坏掉的注册而不是用户的选择，撑不过一小时的授予不花网络
读取去命名一个它保不住的账户）；已授予集合为空的授予在 Microsoft
完成路径自有的那道门被拒。

**轮换后备。** Google 的刷新令牌在刷新时不轮换，所以规则 5 的轮换
写入是极少点火但不可省略的后备：共享令牌源把答案真携带的任何轮换经
同一 sink 落进拨号表的条目与存储，与 Microsoft 路径完全一致，离线
证明驱动脚本化的棘轮端点端到端地证明该路径。

**范围集合，按已交付裁剪。** Google 登录索取 `GOOGLE_SCOPES`（纯的
一半范围表中各用途组的并集）；已交付的账户消费其中：

| Scope | 今日服务的用途 |
|---|---|
| `access_type=offline` + `prompt=consent`（请求参数，不是 scope） | 刷新令牌；完成路径的第一道门拒绝没有它的令牌集（规则 7） |
| `userinfo.email` | 地址查找；无论用户还允许什么都索取 |
| `https://mail.google.com/` | 经账户全局提供商的邮件同步与每一项邮件写入；该组的需求 scope |
| `gmail.settings.basic` | 同意时索取；发件人名写入随账户页切片落地 |
| `https://www.googleapis.com/auth/calendar` | 日历的读写 |
| `contacts`、`contacts.other.readonly` | 同意时索取；Google 上的联系人腿随联系人切片落地 |
| `directory.readonly` | 同意时索取（伴随联系人）；同事目录随其切片落地 |

授予未给的用途不开放，且 Google 允许用户在同意界面取消勾选 scope：
已授予集合按提供商的拼法读回并圈定用途，被扣留的日历以上面拨号的
错误到达，而不是横幅。

**离线证明。** 引擎的 Google 适配器不提供离线重放（其 live 测试以真实
访问令牌门控），存储文档的令牌端点又钉在真实的 Google authority 上，
所以证明在脚本化的回环服务器上跑每一个离线可达的环节：已授予集合挑选
端点的真实 userinfo 查找、共享令牌源的刷新、单飞与经真实 sink 落进
真实拨号表和凭据事务的轮换后备、完成路径的顺序、启动的存储账户拨号，
以及死授予的分类经账户自己的 kind 到达账户行。拨号缝本身在该证明中
是脚本化的；其令牌边界由账户层的拨号测试钉住。真实 Google API 上的
实时证明等待所有者的 Google Cloud 注册，绝不伪造。

## 实时发现证明

harness（docker/harness）把 Stalwart 的 JMAP 监听器以纯 HTTP 发布在
`127.0.0.1:2080`，门控的实时证明（`astra-oauth` 的 `discovery_live`
测试，用 `scripts/dev/harness.sh env` 运行）钉住它实际供应的内容：

- 该来源经 well-known 回退路线给出真实的 RFC 9728 文档（来源的未认证
  GET 以一个不带 `WWW-Authenticate` 挑战的重定向作答，不跟随策略把它
  当作没有指针），命名 `https://mail.example.test` 既是资源也是其
  授权服务器。发现链的前一半实时跑绿。
- Stalwart 还供应声明该签发者的真实 RFC 8414 文档，声明 S256 与一个
  注册端点。harness 域名按设计不解析，所以该文档无法以其命名的签发者
  之下获取，绿色的实时元数据校验不存在。证明改为钉住拒绝：以真正
  供应了该文档的回环来源发问，会在 RFC 8414 第 3.3 节的签发者不匹配
  上闭环失败，这正是阻止被攻破的资源把本应用指向攻击者令牌端点的
  那道检查，对真实服务器的真实文档行使。校验为绿的那一半站在离线
  决策测试之上，它们保住了明文 mock 必须关掉才能跑的每一条规则。

元数据文档之外 harness 不存在 OAuth 服务器：真实登录是提供商切片的
证明，待注册存在后以所有者的账户进行。

## 已知缺口

- **没有注册存在，所以没有用户可见的交付，两个实时证明都没有运行。**
  Microsoft 账户接线（SP2m）与 Google 账户接线（SP2n）都经脚本化服务器
  离线端到端证明交付，但向导的 OAuth 提供对任何人都渲染不出来。
  Microsoft 实时证明（真实的浏览器登录、邮件同步、日历读写、对真实
  端点的刷新轮换）待所有者的 Azure 注册存在时落地；Google 实时证明待
  所有者的 Google Cloud 注册存在时落地，且在应用未通过验证期间，
  Early Access 测试用户允许列表是 Google 自己的门（参考实现的未验证
  应用通知加复选框表面在那变得可达时随之移植）。两者都绝不伪造。若
  Azure 注册最终要求客户端秘密，与公共客户端形状的分歧在其 PR 中升级。
  其余提供商切片消费同一地基：SP2o（JMAP OAuth，一旦 harness 铸造
  授予即可实时证明）、SP2v（IMAP/SMTP OAuth）。
- **重连横幅仅随 Microsoft 家族交付。** Google 没有日历重授权（scope
  在登录时索取；被拒绝的日历是拨号的错误），所以横幅是 Graph 自己的
  表面。过期登录行横跨两个集成家族：拒绝映射按 id 为键、与提供商无关，
  死 google 授予经 google kind 渲染该行，其"再次登录"指向 google
  流程。JMAP 与密码家族等待各自的切片。
- **Microsoft 账户不保存服务器端草稿。** 刷新包装器刻意不声明引擎的
  服务器端草稿能力，所以撰写器只把 Microsoft 草稿留在应用里，直到
  草稿切片接上 Graph 的草稿文件夹。Google 包装器以同一理由做同一裁剪。
- **主体只有 `Me`。** 共享邮箱与其他邮箱推迟：今天一个账户就是它自己
  的邮箱。
- **Google 的联系人、目录与发件人名被索取但未被消费。** 同意界面列出
  `contacts`、`contacts.other.readonly`、`directory.readonly` 与
  `gmail.settings.basic`（集合整体交付，受限 scope 由同一次评估覆盖），
  而会使用它们的腿随联系人、目录与账户页切片落地；Gmail 提供商已经
  转发发件人身份，发件人名写入将落在其上。
- **全邮件 scope 授予永久删除。** Google 的 `https://mail.google.com/`
  连带 Gmail 的不可逆删除；没有任何表面或代理工具提供它，这是 MCP
  切片已记录的同一裁剪。
- **联系人与目录被索取但未被消费。** 同意界面列出
  `Contacts.ReadWrite` 与 `User.ReadBasic.All`（集合整体交付），而
  会使用它们的腿随联系人与目录切片落地。
- **重新授予只以 `login_hint` 定位。** 以另一个地址完成浏览器流程会
  新增第二个账户而不是被拒绝；向导发起的流程同形。钉住目标随提供商
  切片的完成路径改造落地。
- **会话中死掉的授予直到下一次拨号才被察觉。** 同步过程吞掉按账户的
  失败，所以过期行出现在下一次启动，而不是提供商撤销的那一刻。
- **离线的重新启动不做任何分类。** 只有抵达令牌端点的拨号才能回答
  Dead，所以网络回来之前账户页不持有过期行；上一次分类不被持久化
  （规则 12 的"离线时不抑制"约束）。
- **近乎空的授予通过门。** 门拒绝一个 scope 都不命名的授予；只命名
  `offline_access` 的授予通过门、拨号、落进邮件腿的拒绝，而不是一句
  门面话。
- **Graph 日历的显示时区是 UTC。** 宿主尚不携带时区设置；拥有它的
  设置切片替换它。
- **RFC 7591 注册未对真实服务器验证。** harness 声明了一个注册端点，
  但其签发者文档无法以其自己的名字到达，也没有任何注册往返运行过。
- **Windows 浏览器是 OS 默认浏览器。** 复用用户的浏览器会话正是要点，
  代价也随之继承：没有 API 在 scheme 交接后关闭标签页，会留下一个
  空白标签。
- **完成但没有刷新令牌的登录只被集成家族拒绝。** 规则 7 的执行点随
  Microsoft 与 Google 完成路径的第一道门交付；JMAP 与 IMAP 的完成路径
  随其切片落地。
- **一个构建身份，一个 scheme。** 参考实现的打包对开发的 scheme 拆分
  （Windows 按用户注册协议，两个构建认领同一 scheme 会在一个活动中的
  授权码前弹出选择器）在只有一个构建身份存在时没有对应物；规则 8
  记录了届时需要重新审视这一点。
