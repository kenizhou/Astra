# 代理（MCP）访问：Astra Mail 契约

**范围。** SP2k 的 Model Context Protocol 面：stdio 中继、其后的命名
管道监听器、带不可信正文围栏的工具目录、账户门、工具调用台账，
以及承载用户决策的 Advanced 设置面板。对每一个交付其中任何一部
分的表面（今日为桌面宿主）都有约束力。移植来源是 mail-calendar
的 `docs/mcp.md`，按实质移植；下面记录的三处偏差是契约上的全部
差异，每一处都由 Astra 的安全规则手册裁定。

**原则。** *写走用户自己的那扇门。读走另一扇。* 一次写派发的
是点击所派发的同一个写方法，所以助手的标记已读发生在用户自己
的列表里，看得见，并在同一趟到达服务器。读绝不可以这样，原因
有二。每个读形状的 `Intent` 都以快照重建收尾，`Search` 还会改写
当前的查询与范围，一句"我收件箱里有什么"就会滚动并重定一个正在
读别的东西的人的窗口。而 `OpenMessage` 会在服务器上把邮件标记为
已读，一句"给我读读那封邮件"就会悄悄清掉一个未读徽标。因此读走
查询层（`App::query_*`），它什么都不改：不重发布、不移动选中、
不写任何关键词，UI 的缓存也不触碰。`crates/astra-app/src/query/`
中的保证测试钉住这一分野，之后的改动无法把它塌缩回一条路径。

## 传输

```
  MCP 客户端（Claude Desktop、Claude Code、Cursor 等）
        | stdio（JSON-RPC 2.0，换行分帧）
        v
  astra-mcp-relay
  字节中继，零依赖，没有任何协议知识
        | 命名管道（Windows）/ Unix 域套接字（同一代码路径）
        v
  Server                                   crates/astra-mcp
        |-- 读           --> App::query_*（无状态、不改变任何东西）
        |-- 写           --> App 自己的写方法（intent 所派发的那些）
        `-- create_draft --> compose-request 面（不发送任何东西）
```

**为什么要两个进程。** MCP 客户端把自己的服务器当作子进程拉起并
以 stdio 交谈。但正在运行的应用拥有存储、活的 IMAP 连接和内存中
的凭据：一个独立的服务器进程意味着一个存储上有两个写者，以及用
户秘密的第二份副本。中继给了客户端它期待的 stdio，而应用仍是唯
一的所有者，两者之间跨过的只有字节。

**中继是自己的 crate，不链接邮件栈的任何东西，也不懂任何协议。**
不懂帧、不懂版本、不懂 id：它把 stdin 原样拷到端点，把端点原样拷
回 stdout，N 字节进就是恰好 N 字节出，二进制垃圾也一样。除了被
中继的字节，任何东西都不会到达 stdout，一切诊断都走 stderr，因
为 stdout 上多出的一行会让客户端的解析器失步。这也是中继不是
`astra-mcp` 里的一个 `[[bin]]` 的原因：那里的二进制目标会把应用、
引擎和 SQLite 链进一个由别的应用替用户执行的辅助程序。两个方向
天然并发（tokio 的重叠 I/O 客户端），由专门钉住*第二条*消息的测试
保证：Windows 管道会串行化同步 I/O，一个把读停在管道上的中继会
堵死自己的写，恰好答对一条请求，然后挂死所有客户端；测试先发真
实客户端开局的那条通知（它不引出任何回复），再发下一条请求，两
条都必须过得去。

**应用不可达是对 mail-calendar 垫片的一处记录在案的差异。** 垫片
会读到帧里足够的部分，在应用没有运行时回答一个 JSON-RPC
"unavailable" 错误；读取请求的 id 正是本中继拒绝持有的协议知识。
所以中继以非零码退出，诊断在 stderr 上，stdout 保持原样，客户端
报告一个失败的服务器，打开应用即是修复。这是刻意的，且有测试
钉住。

**为什么没有令牌。** 端点在 Windows 上是命名管道，在 Unix 上是
`0700` 目录里的套接字：操作系统用户边界就是认证者，没有需要生成、
存储、展示、粘贴、轮换或防止进入备份的秘密。回环 HTTP 端口才需
要一个，而且它是承重的而非纵深防御，因为任何本地进程都能到达一
个端口。Unix 上每条接受连接的对端 uid 都对照套接字文件的属主检
查。Windows 上边界是管道自身的安全描述符，如实陈述：以默认 DACL
创建的实例服务创建用户、SYSTEM 与 Administrators，
`reject_remote_clients` 让操作系统拒绝从别的机器经 SMB 进来的连
接，`first_pipe_instance` 把名字冲突变成响亮的绑定失败而非劫持。
没有任何令牌或 SID 比较代码，因为在锁定的 tokio 上读取连接进程
的令牌没有安全 API，而本工作区全面禁止 `unsafe`；反向的那几半
（拒绝另一个用户、拒绝远程客户端）由操作系统针对该描述符执行，
在此记录为未覆盖，而不是宣称已测试。

**端点由宿主派生一次，中继从不派生。** Windows 上管道名是应用数
据目录的末段加 `.mcp`，标准目录得到
`\\.\pipe\com.kenizhou.astra.mcp`，旁边的开发数据目录得到另一根管
道：一台机器上的两个构建绝不互偷客户端。Unix 上套接字是数据目录
里的 `mcp.sock`，其父目录只属其所有者（自建为 `0700`，或本已如
此）、套接字本身 `0600`。客户端的配置片段携带宿主派生的确切
值，中继把它原样当作参数，两者永远不会对在哪里碰面各执一词。

## 账户门

默认关闭，用户要自己去找：开关在"设置、Advanced"里（面板自身的
契约见 `settings.md`）。打开服务器与授予一个账户是两个独立的决
定，且账户允许列表默认为空。空即什么也不暴露：`list_accounts`
回答一个空列表，连存在多少个都不说；未列出的账户在每个按账户的
工具上都被拒绝，措辞不区分"未暴露"与"不存在"，因为还有哪些邮箱
存在，本身就是用户没有同意披露的事。不带账户的搜索只跑在被暴露
的账户上，所以一个只被允许看一部分账户的调用者永远不会得到一个
超集。

列表在每次调用时现读，来自一个共享位置，从不在连接接受时截取：
勾选抵达一条已连着的会话，取消勾选立即收回它的访问。

**第三处记录在案的偏差：每次启动门都重新关上。** mail-calendar
把启用标志与账户允许列表跨重启持久化；Astra 两者都不持久化。每
次启动都以服务器关闭、门为空开始，用户亲手重新打开两者，因为规
则手册是失败即关闭，而这个端点是助手能获得的最宽触达。升级说明
随本切片的 PR 走。

## 共同的标准

每一个交付此功能的表面都全部满足。

1. **默认关闭。** 用户去"设置、Advanced"里找它；没有任何提示。
2. **账户允许列表默认为空**，空即什么也不暴露。打开服务器与授
   予一个邮箱是两个独立的决定。未被暴露的账户连名字都不会被提
   及。
3. **发送动词根本不存在，连开关后面的都没有。** 这是第一处记录
   在案的偏差，由规则手册裁定：发送级动词对代理一律拒绝，由人来
   决定并发送。`create_draft` 就是全部：草稿在应用自己的编写器里
   打开，人不按发送就没有任何东西离开设备。没有可以打开的直达
   发送开关，没有需要配置的已知收件人守卫，也就没有会配错的东
   西。
4. **没有垃圾邮件工具。** 第二处记录在案的偏差：Astra 的派发不
   携带垃圾邮件动词，所以不做广告。`add_account`、
   `open_account_setup` 与 `permanently_delete` 因 mail-calendar 自
   己的理由同样保持裁剪：凭据绝不许跨这条通道，弹出的设置窗口是
   钓鱼原语，任何代理都不获得不可逆原语。
5. **正文只来自 `get_message`**，一次一封。列表或搜索只返回主题、
   发件人、日期与旗标。一个返回正文的搜索能一次把五十段恶意文本
   投进模型的上下文，而命中一次就够了。
6. **正文按构造是纯文本**，而非按策略：查询层做了转换，所以走
   该类型的调用者在结构上不可能发出它从未得到的 HTML。HTML 是
   一个严格更大的注入面（隐藏 span、白底白字、CSS `content`），
   消毒哪一样都除不掉。
7. **正文带围栏**，包在 `<untrusted-message-content>` 里，配一行
   前言；试图自行关上围栏的正文会被中和。
8. **没有附件字节跨过边界**：只有名字。
9. **不存在不可逆原语。** `move_to_trash` 交付；`permanently_delete`
   不交付。
10. **端点只有已登录的操作系统用户可达**，如传输一节所述并如实
    划界。
11. **每次调用都入账**（`ai.sqlite` 的 `tool_calls` 表，迁移
    `0011`）：调用自己的关联 id、工具名、结局、时长与参数字符
    数。永远没有查询、地址、主题或正文。入不了账的那一行会让它
    的调用以内部错误失败关闭，绝不放行未入账的调用。

### 如实说明这防不住什么

邮件正文是攻击者写的文本，正在进入模型的上下文。这无法修复，只
能设界，上面的条目是强度各异的界。围栏是最弱的：它对模型只是一
个建议。`create_draft` 是一个人类可见的步骤，不是安全保证：要求
"回复 Bob"的用户会不读就按发送。Astra 的形状真正给出的是规则手册
画下的硬界：没有可以绕过口才的发送工具，发送的时刻始终是人手按
在应用自有的按钮上。

还有一句"没有令牌"绝不能被读成暗示。任何同用户进程本来就读得了
应用的数据目录，所以这里没有授予任何原本不存在的权限。但它是可
达性上的一级台阶：直接读存储需要一个懂得 schema 的蓄意攻击者，
而一个有文档、有公开工具清单的端点是一个可被发现的 API。这是真
实差异，也是如实的说法。

最后：已连接的助手读到什么，它自己的提供商按其政策也可能收到。
如果它是云端助手，用户一让它读什么，邮件内容就离开了设备。那是
用户对自己选定的一方的差遣。

## 工具集

`snake_case`，draft-2020-12 schema，`additionalProperties: false`，
标注如实填写，因为客户端据此展示确认弹窗。`account` 与 `key` 总
是成对出现，与 `MessageRef` 一致：provider key 只在账户内唯一，
所以错误的跨账户路由在这一边界同样无法构造。每个携带邮件的结果
都把两者原样带回。

| 工具 | 输入（粗体为必填） | 标注 |
|---|---|---|
| `list_accounts` | 无 | `readOnly` |
| `list_folders` | **`account`** | `readOnly` |
| `list_messages` | **`account`** `folder` `unread_only` `offset` `limit`（1 到 50） | `readOnly` |
| `search_messages` | **`query`** `account` `folder` `offset` `limit` | `readOnly` |
| `get_message` | **`account`** **`key`** | `readOnly` |
| `mark_read` | **`account`** **`key`** **`read`** | `idempotent` |
| `set_flagged` | **`account`** **`key`** **`flagged`** | `idempotent` |
| `archive_message` | **`account`** **`key`** | `idempotent` |
| `move_to_trash` | **`account`** **`key`** | `destructive`、`idempotent` |
| `create_draft` | `account` **`to`** 列表 `cc` 列表 `bcc` 列表 **`subject`** **`body_text`** `reply_to` | 无 |

读一封邮件绝不把它标记为已读：`get_message` 走查询层，端到端证明
断言读后跨一次刷新该行仍未读。

## 执行

自动化：

- `crates/astra-app/src/query/` 及其套件：两条保证（读不重发布任
  何东西、不写任何关键词），配上 `OpenMessage` 确实写 `$seen` 的
  对照，以及窗口分页契约。
- `crates/astra-mcp/src/fence_tests.rs`：围栏、其前言、被中和的自
  闭合标签。
- `crates/astra-mcp/src/tools_tests.rs` 与 `bridge_tests.rs`：schema
  字面量与输入类型互检、账户门的空即不暴露、列表无正文规则、分
  页钳制，以及对缺席的发送与垃圾邮件工具的显式钉住。
- `crates/astra-mcp/src/server_tests.rs` 与 `ledger_tests.rs`：分帧、
  还价握手、错误封套、台账行的形状（只有计数与 id，含多字节字
  符），以及入不了账时的失败关闭拒绝。
- `crates/astra-mcp/src/transport_tests.rs` 与
  `transport_pipe_tests.rs`：端点派生，以及真管道上的畸形 id 泄漏
  钉。
- `crates/astra-mcp-relay/tests/relay.rs`：跑构建出的二进制、真管
  道、真 stdio：字节数钉、以第二条消息为核心的往返、应用不可达
  偏差、用法错误。
- `client/desktop/src/mcp_tests.rs`：宿主的启停接缝、名字被占的失
  败态、允许列表接缝抵达活连接上的门。
- `crates/astra-mcp-relay/tests/e2e/`：门控的端到端与实测证明，
  跑在运行中的测试具上。中继把 stdio 桥到管道，其后是架在真两账
  户应用（产品自己的证书接受拨号）之上的服务器；穿过这整个栈：
  握手、十条工具目录且发送的裁剪以缺席可见、与窗格一致的同一些
  文件夹名、三封种子邮件按新到旧且任何行都无正文、某一封种子邮
  件的带围栏纯文本（且读后跨刷新该行仍未读）、经门的集合形式跑
  引擎真搜索、一次 `mark_read` 的翻转出现在应用自己的列表里并跨
  刷新存活、把语料复原如初，以及未被列出的已配置账户经中继、服
  务器与门一并拒绝、`list_accounts` 不提其名、与一个无人持有的
  id 得到同样的拒绝措辞。

手动，每个发布版本在桌面上：

1. `scripts/dev/harness.sh up`，启动桌面，连接测试具账户，同步一
   次。
2. "设置、Advanced"：打开它，暴露测试具账户，复制片段，确认状态
   行显示运行中。
3. 把片段粘进真实 MCP 客户端的配置，重启客户端，在其日志里确认
   握手与工具发现。
4. 一个完整回路：列出收件箱，读一封并断言它在应用里仍未读，标
   记已读并看行翻转，起草一封回复并断言预填的编写器已打开、未
   发送。一次会话里至少做两次工具调用：恰好能答一条请求的中继
   在第二条之前看起来完全健康。
5. 反向项：关掉它并确认下一次调用干净地失败；取消暴露所有账户
   并确认调用报告什么都没有；退出应用并确认客户端显示服务器不
   可用而非挂死。
6. 台账读取（对应用的 ai.sqlite 走 AiStore::recent_tool_calls，或
   直接以 sqlite 读 tool_calls 表）：确认读没有在存储里留下痕迹，
   且每次调用恰好留下一条不含内容的台账行。

## 已知缺口

- **中继尚未随安装版应用捆绑。** 片段派生的中继路径，桌面安装包
  还没有放置它；这一步归打包步骤。开发构建能在 cargo 构建处找到
  二进制，端到端证明拉起的就是那个二进制，所以契约本身已被证
  明；欠的只是安装版的放置。
- **Unix 传输半边已实现但未钉。** `0700` 目录、`0600` 套接字、陈
  旧套接字的接管与对端 uid 拒绝在 Unix 上可编译；本宿主是
  Windows，`cfg(unix)` 的测试随第一条 Unix CI 落地。盲写跑不起来
  的测试不是测试纪律。
- **Windows 对端检查的反向项由操作系统执行，未被测试覆盖。** 另
  一个用户与远程客户端由管道描述符拒绝；复现其中任何一个都需
  要第二个账户或第二台机器，本测试具两者皆无。
- **允许列表按账户列，不按文件夹。** 被暴露的账户暴露应用为它读
  的每一个文件夹。
- **代理的草稿走 compose-request 快照的回复种类。** 快照词汇早于
  代理草稿，没有"新邮件"的拼写，所以全新的代理草稿打开时不带线
  程信头，其 `bcc` 同理不预填。两者随 compose-request 契约长出代
  理形状而收窄。无论哪种，什么都不发送：编写器打开时显示的正是
  它将发送的内容。
- **编写器关闭时创建的草稿在下一次聚焦时打开，而非立即**：代理
  边车的接缝与其时序，不是新问题。
- **`App<P>` 之上的端口按设计只有薄委托。** 其行为钉在它所委托
  的各层里，并由真管道上的门控端到端整体驱动。
