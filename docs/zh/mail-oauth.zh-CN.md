# IMAP/SMTP OAuth 登录：Astra Mail 契约

**范围。** 提供商提供浏览器登录的 IMAP/SMTP 账户如何接入：安装界面在
问用户之前先问服务器什么、授权服务器从哪里得知、客户端如何注册自己、
以及令牌开始过期后账户如何表现。对每一个提供邮件登录的界面、每一个
消费其 grant 的账户都有约束。实质上移植自 mail-calendar 的
`mail-oauth.md`（十一条规则），按 Astra Mail 今日实际交付的范围裁剪；
分歧在遇到处记录，缺口列在文末，绝不静默略过。

[`provider-oauth.zh-CN.md`](provider-oauth.zh-CN.md) 是 Microsoft 与
Google 的契约，它们的端点与客户端注册由构建在编译时持有。这一篇属于
其他所有提供商：一台冷接触的服务器，完全依标准发现，不点任何厂商的
名。

**原则。** *先问服务器，任何未命中都是密码输入框。* 一个域名可以为其
网页会话发布授权服务器，而在 IMAP 上只收密码；基于那种证据提供的登录
铸造的是邮箱会拒绝的令牌。所以由邮箱自己的能力行裁决，不向它呈现任何
东西，未被回答的问题归结为在任何地方都可用的那一个答案。

## 规则

1. **先问服务器。** 在任何 OAuth 发现之前，安装路径对用户指名的邮件
   服务器开一条 TLS 连接，读它的预认证 `CAPABILITY`（引擎探针动词之上
   的 `astra_account::imap_auth_offer`）。不呈现任何东西，也不记录任何
   失败登录：探针停在能力行，以 `LOGOUT` 关闭，绝不发送凭据。拨号运行
   在向导建立的信任之下，所以证书被接受的服务器被询问的方式与随后接入
  它的拨号完全一致；一张被接受的证书同时覆盖 IMAP 腿与 SMTP 提交腿，
   因为两条腿指名同一台服务器。

2. **三个答案，因为它们是三块屏幕。**

   | 服务器说 | 安装提供 |
   |---|---|
   | 一种 OAuth 机制，且找到了本次安装可以注册的授权服务器 | **登录**，主按钮。密码输入框在密码也可用时藏在次级控件之后。 |
   | 一种 OAuth 机制，但没有可用的授权服务器 | 一句话说明该提供商只承认它预先注册的应用，外加密码输入框。 |
   | 没有 OAuth 机制，或什么都没有（不可达、超时、证书尚未被接受） | 密码输入框，与从前完全一样。 |

   中间一行正是这是枚举而不是布尔的原因。登录存在却对本次安装关闭的
   提供商，与根本不提供登录的提供商不是一回事，而对两者都只给一个光秃
   秃的密码表单，会让人纳闷同事有的按钮自己为什么没有。**藏在之后意味
   着被问到才绘制**：登录按钮立在正文里，下方是"改用密码"；选择它才
   绘制输入框；输入框绝不移除，且只在服务器自己承认没有密码时才完全
   隐藏。

3. **只在密码可用时提供密码。** IMAP 腿上的 `AUTH=PLAIN` 或
   `AUTH=LOGIN`，或没有 `LOGINDISABLED`；提交腿上只看 `AUTH` 行，因为
   提交要么经 SASL 认证要么不认证。关掉了密码认证的服务器得不到密码
   输入框：那会是一条没有人走通的死路，要走到打完密码才发现。

4. **签发者来自提供商自述，绝不来自第三方。** 两条通道，按序：提供商
   自己 autoconfig 的 `<oAuth2><issuer>`（自动发现 crate 在字段过界
   之前解析并做信任过滤：ISPDB 的块与任何不可信跳都被丢弃）；不行则
   对**电子邮件域名**、再到其可注册域名做 RFC 8414 well-known 探测。
   从文档里只取签发者；旁边的端点被忽略，真正的端点来自该签发者自己的
   元数据。JMAP 服务器的问法不同且仅在那里：它是 HTTP 资源，自己未认证
   的 `401` 会指名其授权服务器（RFC 9728），IMAP 没有对应物，这正是
   上面探针存在的原因。

   **记录在案的选择：可注册候选取电子邮件域名的。** 参考实现把第二个
   well-known 候选表述为邮件服务器的可注册域名；规格的表述，也就是本
   构建实现的，是电子邮件域名的。只要邮件服务器位于地址自己的可注册
   域名之下，两者重合，凡凭地址相遇的提供商皆如此。两者在自定义托管
   域名上分歧（`mydomain.example` 的地址，其邮件托管在运营商域名之
   下）：那里参考实现会找到运营商的签发者，而本构建回答
   RegistrationNeeded 并让密码站着，这是本构建无法指名的提供商所得的
   诚实屏幕。真实世界遇到托管域名时再议参考实现的形状。

5. **客户端 id 是注册来的，绝不是发明的。** 元数据声明
   `registration_endpoint` 时，本次安装注册自己（RFC 7591），签发的 id
   随账户持久化，所以启动绝不重复注册，后来撤回开放注册的服务器也破坏
   不了已有 id 的账户。同一会话内的重复尝试复用已铸的 id：没有这一条，
   一次不稳定的登录点三下就会在用户的账户上留下三个孤儿客户端注册。

6. **不做开放注册的提供商需要本构建携带的条目，缺省是受支持的构建。**
   `astra_oauth::static_mail_providers` 持有端点与主机模式，按服务器
   主机在标签边界上匹配；客户端 id 构建时注入，id 缺失的路径不提供。
   只签发机密客户端的提供商是要去跟他们提的，不是要绕过的：安装的二
   进制保不住秘密，为显得合规而嵌一个是比规则 2 的诚实句子更糟的
   做法。

   **记录在案的选择：表格交付为空，其优先级是静态优先。** 本构建持有
   的条目胜过发现，因为预注册的客户端携带提供商审阅过的 scope，动态
   铸造的没有。客户端 id 为空白（注入缺省）的条目被跳过而不算路径，
   留给发现作答，因此条目可以先于其注册交付端点而不关闭该服务器的可
   发现路径。在条目存在之前，规则 2 的中间行就是每个封闭注册提供商
   所得，它说的是真话而不是什么都没说。

7. **每一次失败都是密码输入框。** 被拒的拨号、解析不了的元数据文档、
   被拒的注册、不回答的服务器、尚未被接受的证书：全都意味着问题未被
   回答，而任何地方都可用的答案是密码。安装界面绝不为此显示错误；放弃
   在哪一步，写在诊断日志里，那里才有用。

8. **服务器回答之前卡片上没有任何可操作的东西，且一个时限与询问
   赛跑**（10 秒，宿主命令自己的约束，旁边还有卡片的保险赛）。询问等
   字段落定（400 毫秒；每次击键一探是对服务器从不需要问的问题），决策
   把自己的工作限定在时限之内（能力探针 3 秒、签发者搜索 6 秒，到点即
   服务器未答与签发者未找到），屏幕只由最后落地的答案绘制：对被编辑
   字段的重新询问保持站立的屏幕，凭据输入框绝不会被画出来又被收走。
   询问从不需要密码：宿主以 grant 形状的凭据构建问题，所以在输入任何
   东西之前就能问服务器。

9. **凭据按拨号解析，一次认证失败只值一次重拨。** 访问令牌在一小时内
   过期而 IMAP 会话不会，所以只构建一次的配置只在其第一枚令牌的时长内
   通过认证。引擎刻意什么都不自行刷新：账户的每次拨号向共享令牌源
   （单飞、重放冷却、经宿主 sink 的轮换）要一枚当下有效的令牌，被拒的
   令牌经同一源恰好续期一次后拨号才放弃，因此一阵拒绝只花一次刷新而不
   是每条腿一次。SMTP 提交腿以它自己的机制选择呈现同一枚令牌。密码
   账户上这些都不跑：同一个秘密会回到同一台服务器，而提供商可能在朝
   锁定计数。

10. **OAuth 账户任何地方都不存密码。** grant 只存一份，作为账户文档的
    `[imap.oauth]` 块（客户端 id、刷新令牌、发现的端点、重定向、
    scope、RFC 9207 适用时的签发者），SMTP 腿呈现同一来源而不是复用的
    密码。"修复此账户"是重新授权，绝不是输入的秘密；该家族绝不与
    JMAP 或集成家族共享 grant：一个账户、一个凭据、一次拒绝、一种
    补救。

    **记录在案的选择：这条链没有邮件访问 scope 门。** JMAP 链拒绝其
    元数据声明的 scope 不授予邮件访问的文档，因为一个什么都换不到的
    JMAP 令牌会很久之后才以空邮箱现身。这条链不带这样的门：参考实现
    不要求 SASL 有一条（服务器可以接受令牌并施加自己的默认授予），
    而 SASL 腿对无用 scope 的回答是一次被拒的认证，过期行已经指名了
    它。与 JMAP 链的不对称是刻意的，记录在此而不是抹平。

11. **服务器说自己发 `iss` 就严格校验**（RFC 9207）。那是 `state` 匹配
    之后唯一能抓住混淆中继的东西，且严格校验：声明要发的服务器少了该
    参数的响应被拒绝，因为删掉一个查询参数不能就是关掉校验的全部。
    什么都没声明的服务器没有可比较的，那是 RFC 9207 之前的状态，不是
    故障。

## Grant、拨号与界面

完成路径完全照 JMAP 的模型：令牌源在拨号**之前**注册进拨号表的条目，
拨号中途落地的轮换有处可去，最终持久化读条目而不是拨号前一刻解析的
副本。首次添加经事务的 `add` 持久化，拨号被拒时整个注册回滚；对已
站立账户的重新同意走 `rotate`，grant 旁边保持已存的形状。令牌组不带
刷新令牌的 grant 在第一道门被拒（`offline_access` 已被索取），拒绝带
分类词呈现，绝不沉默。

启动时，启动拨号把死 grant 分类为它随后跳过的账户的过期登录态：账户
页渲染 imap_smtp 家族指名被拒凭据的行（绝不是断线徽章），其补救是
重新连接账户：邮件授权不与 JMAP 家族的重授权臂共享（那些以 JMAP 节
与该族的授权形状定类型），因此邮件族自己的重授权臂是有意的后续切片，
而非期待。

## 刻意不做的事

- **不做 RFC 7628 挑战探测。** 服务器拒绝令牌时返回的挑战可以描述其
  OAuth 配置，客户端可以借呈现一枚故意无效的令牌来发现授权服务器。
  那会在用户尚未登录过一次之前，在最可能放弃的屏幕上，留下一笔失败的
  认证记录；何况该字段是可选的：Stalwart 对坏令牌只回答一句裸的
  `NO [AUTHENTICATIONFAILED]`，没有任何挑战。
- **不发 RFC 8707 `resource`。** 该 profile 没有为 IMAP 端点定义 URI
  形状；按 resource 划分令牌作用域的服务器没有它就施加自己的默认，
  捏造 `imap://` 会让交换与其后的每次刷新都冒 `invalid_target` 的险。
  JMAP 账户仍发送其 RFC 9728 元数据发布的那一个。
- **没有机制旋钮。** 哪个 SASL 机制携带令牌由引擎按服务器声明协商，
  能钉死它的调用方等于在编码自己正对话的提供商。

## 证明

离线套件在脚本化服务器上扛着整条链：观察到的能力行上的三个答案、按序
的签发者候选、注册缓存、grant 的往返、按拨号的凭据与其唯一续期、完成
路径的次序、死 grant 的行、各屏幕的渲染。门控实时套件钉住只有真实
服务器能给的，对着本地 Stalwart harness：经引擎自己的探针动词读两条腿
上的能力行（IMAP 预认证行与提交腿的 EHLO AUTH 行，读自产品自己的 TLS
接受之行），在真实拨号的服务器上组合出 registration-needed 形状的
决策，以及对 harness 那个不解析域名的发现的软失败：签发者链在预算
之内回答它的未命中，未被接受证书的被拒拨号回答密码屏幕。

完整的登录往返在那里不可证明：harness 不供 OAuth 签发者，这是 JMAP
切片的发现。该证明等待真实的身份提供商，与 JMAP 的完全一样，绝无
伪造。

## 已知缺口

- **静态提供商表交付为空**：没有注册的提供商 id，没有提供的路径，在
  条目存在之前每个封闭注册的提供商都得那行诚实的中间行。
- **完整链的实时证明等待真实的身份提供商**（harness 不供签发者）；
  探针与发现的软失败是实时钉住的两点，完整链离线跑在脚本化服务器上。
- **密码家族的过期行是密码家族自己的**（被拒的密码），原样未动：账户
  行早已报告它，本切片新增的 imap_smtp 行指名的是被拒的 OAuth 凭据。
- **RFC 7628 挑战探测与 RFC 8707 resource 留在外面，没有机制旋钮**，
  与上面的刻意裁剪所记录的完全一致。
