# JMAP 账户：Astra Mail 契约

**范围。** JMAP 账户在 Astra Mail 中是什么：它保存的那一个凭据、安装向导推导的
基础 URL、账户身份与整个账户同步所经的那一个 provider、在服务器宣告可发现
OAuth 时以浏览器登录接入的方式，以及展示它的各个界面。对每一个搭载 JMAP
账户的界面都有约束。实质上移植自 mail-calendar 的 `agent-guidance/jmap.md` 与
`providers.md`，并按 Astra Mail 今日实际交付的范围裁剪；缺口记录在文末，绝不
静默略过。

**原则。** *一个 JMAP 账户就是一个基础 URL、一个凭据，以及服务器自己的
session 所说它拥有的一切。* 关于 JMAP 账户没有任何东西是猜出来的：能力
（mail、submission、calendars）读自拨号取回的 session 资源，认证方案由服务器
自己的 `401` 挑战指名，账户级的作用域意味着一条连接服务全部文件夹。Astra
不为这一族添加任何 per-provider 知识；标准本身就是 provider。

## 唯一的凭据

一个 JMAP 账户只保存一个凭据，存为 `password`，无论用户粘贴的是什么：登录
密码、应用专用密码，或 API token。三条规则把它钉在唯一：

- **带用户名的形式严格更强。** 凭据与账户的电子邮件地址一起保存（地址即
  用户名），引擎传输层将其作为 HTTP Basic 呈现，或在服务器挑战 Bearer 时改写
  为 Bearer，因此一种保存形式即可服务于一个会改变线上格式的服务器。裸
  token 没有用户名，无法构造 Basic 头。
- **遗留的 `token` 键在加载时折叠进 `password`。** 在两个字段合并为唯一之前
  写下的文档仍可接入；折叠保留 `token` 的值，即该账户最后一次连接所用的
  凭据。该键只读取并折叠，不再写出，任何代码路径都永远不会同时看到两个
  凭据。
- **浏览器登录接入的账户保存的是 grant，二者绝不并存。** `[jmap.oauth]` 块的
  refresh token 是该账户的唯一凭据；一个不知何故同时带有密码与 grant 的文档
  以 grant 为准：该账户是通过登录接入的。宿主绝不会两者都写。

唯一凭据规则是承重的加固，不是整洁偏好：为一个账户同时保存密码与 token 的
客户端持有两个可能对各自权限意见不一的凭据，服务器吊销其中任何一个，都会
表现为账户以某种保存形状无法指名的原因失败。一个凭据、一次拒绝、一种补救。

## 基础 URL

安装表单的服务器字段经由一个推导解析，每一份已保存的 JMAP 文档与每一次连接
都走同一条，因此一个发现的账户与一个手填的账户不可能对它们指的是哪台服务器
产生分歧：

- **留空**推导为 `https://<电子邮件域名>`，依赖 RFC 8620 在
  `/.well-known/jmap` 的自动发现。
- **裸主机**补上 `https://` 前缀。
- **显式的 `http://` 仅对回环主机保留**（字面 `localhost`，或任意记法的回环
  IP）。对任何其他主机它被升级为 `https://`，因为真实账户永远拨 TLS，而对
  公网服务器输入 `http://` 的人指的是那台服务器，而不是明文。这与自动发现
  crate 对同一 origin 类别持有的发现规则一致。

## 身份与拨号

JMAP 账户的 id 是 `address@jmap:<host>`（解析出的主机，小写），因此它既不与
同一地址同一主机的 IMAP 账户冲突，也不与 OAuth 各族的 `address@graph` 与
`address@google` 冲突。该标记不可能出现在真实的 IMAP 服务器名里，id 空间保持
不相交。

拨号为**整个账户连接一个 provider**。JMAP 的 mail 作用域是账户级的，每封邮件
自带 `mailboxIds` 成员关系，因此一条连接同步全部文件夹，没有按文件夹绑定的
provider；在第一趟之前打开的文件夹重连的是这同一个账户级 provider，而不是
另铸一个新的。拨号从 session 快照的能力决定账户拥有什么：mail、submission 与
calendars 读自服务器自己的 session 资源，绝不从配置猜测，日历读取恰好依托该
宣告（一个不提供 calendars 能力的 session 就不为该账户提供日历界面）。

整条腿的证明是带门禁的实活：密码账户在真实 JMAP 服务器上接入，一次刷新即经
那一个 provider 列出账户的文件夹，预置的笔记以最新在前渲染，一封富格式笔记
经产品自己的阅读管线打开，一次发送往返到第二个 JMAP 账户且发件人副本归档于
Sent，session 宣告的日历读入日历界面。套件撤回它发出的一切，因此服务器为
钉住它的套件保持原状。

## OAuth 登录

宣告可发现 OAuth（RFC 9728）的 JMAP 服务器提供了第二种接入方式，任何地方都
没有 per-provider 代码：这条链就是标准本身，客户端自行注册，Astra 不指名任何
厂商。

- **发现链是 RFC 9728 到 RFC 8414 到 RFC 7591。** session URL 上的
  protected-resource 文档指名授权服务器；授权服务器的元数据指名各个端点，
  以及（若发布）注册端点；动态注册铸出客户端。不发布注册端点的服务器无法
  向其提供登录，因为没有办法成为客户端。
- **永远软失败。** 链上任何一步未命中都让密码字段留在原地，绝不报错：向导
  只在服务器自己的宣告支持时提供登录，服务器不提供的用户看到的是普通的
  密码表单。offer 探测只是读取服务器自己的文档，仅此而已。
- **注册按会话缓存。** 动态注册每次调用都铸出新的 client id，若不缓存，
  每次取消或失败的尝试都会在用户账户上遗留一个孤儿注册。缓存以
  `(issuer, redirect_uri)` 为键；一旦登录完成，client id 随账户持久化，不再
  发生任何注册。
- **PKCE 才是真正的保护。** 客户端以 public 身份申请，不携带机密 secret；
  罕见服务器签发的 client secret 会被保存与发送，但安装的应用守不住
  secret，也没有任何逻辑依赖它。

grant 持久化为 `[jmap.oauth]`：client id、refresh token、发现的端点、注册时的
redirect URI（每次刷新逐字重放，否则服务器拒绝该 grant）、scopes，以及这条链
后来的 RFC 增加的两个字段。**resource indicator**（RFC 8707）被持久化，是因为
每次刷新都必须重发它：签发 resource-scoped token 的服务器在没有它时回答
`invalid_target`，这会让账户在第一次刷新而不是在安装时坏掉。**issuer**
（RFC 9207）被持久化以校验重新授权的 `iss` 参数；缺席意味着没有可比较之物，
这是 RFC 9207 之前的状态，不是破坏一个可用账户的理由。

### token source 维持账户存活

grant 的 access token 由 Graph 族已在使用的共享 token source 铸出并保持存活：
single-flight（一次铸出在途，所有调用方等待它）、重放冷却（并发的 401 爆发
只花费一次刷新，而非每个调用方一次），以及轮换直写。provider 外的包装层在
token 转向时重建连接，能力从新代理自己的 session 重新快照，绝不沿用。

轮换直写就是 Fastmail 规则，在这里约束最硬：棘轮式服务器在重放 refresh
token 时吊销整个 grant，因此一次没人保存的轮换会在下次启动时杀死账户。
token source 看到的每一次轮换都在调用方继续之前落入宿主的 token sink，而
无法写入存储的启动仍然连接（只读），而不是静默跳过持久化。

### 完成时的顺序

完成先拨号后持久化，且 dial-table 条目先注册：拨号中途发生的轮换落入该条目，
最终持久化读取 dial table，绝不读取解析副本。完成拨不通的 grant 在任何东西
被保存之前即被拒绝，因此没有账户站在一个服务器刚刚拒绝的凭据上。

## 向导一臂

安装表单在标注 "Password or API token" 的字段下询问那一个凭据，服务器 URL
可编辑，并在查询没有携带时从电子邮件域名推导。当 offer 探测说服务器宣告可
发现 OAuth 时，字段旁有一个登录按钮；该按钮在系统浏览器打开授权 URL，完成
等待重定向。浏览器打开期间关闭表单会取消登录，因此被放弃的尝试既不搁置
等待者，也不遗留注册。

## 已知缺口

- **没有就地续期。** 存储凭据被拒绝的 JMAP 账户显示指名该凭据的过期登录
  行，其补救是移除账户并重新接入。保留邮件、文件夹与设置的就地 re-grant
  等待它的切片（能力行保持开放）。
- **会话中途死去的 grant 要到下一次拨号才会被察觉。** 启动拨号会归类死
  grant；没有任何东西在应用运行期间监视会话中降临的吊销。
- **联系人（RFC 9610）属于后续切片。** 引擎的 JMAP 联系人面尚未在 Astra
  浮出；session 对它的宣告不改变产品今日展示的任何东西。
- **发件人姓名写入等待它的切片。** submission 能力提供的 identity 动词尚未
  为 JMAP 账户浮出。
- **被拒绝的重新同意可能把 dial table 回滚越过一次已落地的轮换。** 重新授权
  流程的失败路径整体恢复先前的存储文档；在流程开始与拒绝之间落地的轮换随之
  丢失。Graph 与 Google 族共享这一形状，在那里也有记录。
- **与 provider 的 IMAP/SMTP 登录仍是独立一族**（mail-oauth 契约）；JMAP
  账户的 OAuth 是 JMAP 自己的，从服务器发现，两者绝不共享 grant。
- **OAuth 链的实活证明钉住其诚实的一半。** 测试服务器给出 RFC 9728 文档
  （其 authorization_servers 指名一个无法解析的 issuer，即 provider-oauth
  发现证明记录的那一发现），因此带门禁的套件把软失败拒绝钉为实活：不提供
  登录，密码字段留在原地。完整链路的实活证明等待一个真实的 JMAP 身份提供
  方，在此之前离线套件以脚本服务器承载完整链路。
